# Audit Pipeline

Skill นี้เป็น workflow มาตรฐานสำหรับตรวจสอบความสอดคล้อง (consistency) ของเอกสารทั้งสายงานใน
โปรเจกต์นี้ ตามลำดับชั้น: spec (`01-spec/`) → `backlog.md` →
`feature-list.md`/`user-journey.md` → จากนั้นแยกเป็น **3 สาขาขนานกัน** ที่ต่างพึ่ง
`feature-list.md`/`user-journey.md` เหมือนกันแต่ไม่ขึ้นต่อกันเอง:
- **(ก) เอกสารทดสอบ** ใน `docs/03-testing/01-test-plan/` (`acceptance-criteria.md`,
  `test-plan.md`, `test-cases/`)
- **(ข) Prototype** ล่าสุดใน `docs/02-design/01-prototypes/`
- **(ค) เอกสารเชิงเทคนิค** ใน `docs/02-design/02-technical/` — ภายในสาขานี้เองมีลำดับชั้นย่อย
  ต่อเนื่องกัน 4 ชั้น: `architecture.md` → `api-spec.md`/`db-spec.md` → `detailed-design/` →
  `nfr-review.md` (ดูรายละเอียดใน `sync-technical-spec`)

โดยรันตรวจ (และแก้ไขถ้าจำเป็น) ไล่จากชั้นต้นทางไปชั้นปลายทางตามลำดับ **ไม่ใช่รันขนานข้ามชั้น**
เพราะแต่ละชั้นต้องใช้ผลลัพธ์ที่อัปเดตล่าสุดของชั้นก่อนหน้าเป็นแหล่งความจริงเสมอ — ถ้ามีการแก้ไขชั้นใด
ชั้นหนึ่งล่าสุดกว่าชั้นอื่น การไล่ตามลำดับนี้จะจับส่วนต่างที่ไล่ลงมาได้ครบทุกชั้น ไม่ตกหล่น
(สาขา (ก), (ข), (ค) เองรันตามลำดับก่อนหลังกันได้ เพราะไม่ได้ขึ้นต่อกัน แต่ทั้งสามต้องรอ
`feature-list.md`/`user-journey.md` เสร็จสมบูรณ์ก่อนเริ่มเสมอ)

สาขา prototype และขั้นตอน `nfr-review.md` ในสาขา (ค) เป็นจุดเดียวที่**ตรวจสอบและรายงานเท่านั้น
ไม่ auto-fix** เพราะการสร้าง/แก้ prototype ต้องมีขั้นตอนยืนยัน scope กับผู้ใช้แบบโต้ตอบเสมอ และ
การแก้ NFR gap ต้องย้อนกลับไปแก้ที่ชั้น architecture/api-db/detailed-design ซึ่งมี agent เฉพาะ
ของมันเองอยู่แล้ว (เป็นการตัดสินใจเชิงเนื้อหาที่ agent ตรวจสอบอย่างเดียวไม่ควรข้ามไปทำแทน) ส่วน
สาขา (ก) และชั้นย่อยส่วนใหญ่ของสาขา (ค) **auto-fix ได้เต็มรูปแบบเหมือนชั้น backlog/feature-list**
เพราะต้อง cover ครบทุก FR/NFR เหมือนกันเสมอ ไม่มีการเลือก scope บางส่วนแบบ prototype

**เอกสารทั้งหมดในสาขา (ค) ตั้งใจเขียนแบบไม่ผูก tech stack** จนกว่า `technology-stack.md` จะถูก
ตัดสินใจแล้วจริง — ถ้าพบว่า subagent ใดในสาขานี้ระบุชื่อ technology/framework/database engine
ใดๆ ให้ถือว่าผิดกฎ (ดูข้อควรระวัง)

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: ใช้ค่าวันที่ปัจจุบันที่มีอยู่ในบริบทของคุณ (รูปแบบ `YYYYMMDD`) เพื่อส่งต่อ
   ให้ subagent/skill ทุกตัวใช้กับไฟล์ log ของวันนี้ — subagent ทั้งหมดไม่มีเครื่องมือ Bash จึงหา
   วันที่เองไม่ได้ ต้องส่งมาให้ใน prompt ทุกครั้ง

2. **ชั้นที่ 1 — spec ↔ backlog**: เรียก subagent `backlog-auditor` ผ่าน Agent tool
   (`run_in_background: false` เพราะอาจต้องถามผู้ใช้แบบโต้ตอบผ่าน AskUserQuestion กรณีเจอ
   รายการกำพร้า) พร้อมบริบทว่านี่คือ session สนทนากับผู้ใช้จริง แล้วรอผลลัพธ์ก่อนไปขั้นตอนถัดไปเสมอ

3. **ตรวจสอบผลลัพธ์ชั้นที่ 1**: สุ่มอ่าน `docs/01-requirements/backlog.md` จริงอย่างน้อย 1-2 จุด
   ก่อนไปต่อ ห้ามเชื่อรายงานของ subagent 100% โดยไม่ตรวจเอง ถ้า subagent รายงานปัญหาเชิงโครงสร้าง
   ที่ทำให้ตรวจต่อไม่ได้ ให้หยุด pipeline ทันทีและรายงานผู้ใช้ ไม่ไปขั้นตอนถัดไป

4. **ชั้นที่ 2 — backlog ↔ feature-list/user-journey**: เรียก subagent `feature-journey-writer`
   ผ่าน Agent tool (`run_in_background: false`) **ต้องรอชั้นที่ 1 เสร็จสมบูรณ์ก่อนเสมอ** เพราะ
   ชั้นนี้ต้องใช้ `backlog.md` เวอร์ชันล่าสุดหลังชั้นที่ 1 แก้ไขแล้ว (ไม่ใช่เวอร์ชันก่อนตรวจ) เป็น
   แหล่งความจริง

5. **ตรวจสอบผลลัพธ์ชั้นที่ 2**: สุ่มอ่าน `feature-list.md`/`user-journey.md` จริงอย่างน้อย 1-2 จุด
   เช่นเดียวกับข้อ 3 (รวมถึงตรวจว่าทุก journey มี mermaid block กำกับ) ถ้าพบปัญหาเชิงโครงสร้าง
   ให้หยุด pipeline และรายงานผู้ใช้เช่นกัน

6. **สาขา (ก) — feature-list/user-journey ↔ เอกสารทดสอบ (auto-fix)**: เรียกผ่าน **Skill tool**
   ด้วย `skill: sync-test-plan` (ไม่ใช่เรียก subagent `test-writer` ตรงๆ) เพราะ skill นี้มี
   logic การ auto-chain ไป `requirement-writer`/`sync-feature-journey` ในตัวอยู่แล้วเผื่อ
   `test-writer` เจอสถานการณ์ที่ยังไม่มี FR/NFR รองรับระหว่างเขียน acceptance criteria — **ต้องรอ
   ชั้นที่ 2 เสร็จสมบูรณ์ก่อนเสมอ** ด้วยเหตุผลเดียวกับข้อ 4

7. **ตรวจสอบผลลัพธ์สาขา (ก)**: สุ่มอ่าน `acceptance-criteria.md`, `test-plan.md`, และไฟล์ใน
   `test-cases/` จริงอย่างน้อย 1-2 จุด ก่อนไปสาขาถัดไป ถ้า `sync-test-plan` รายงานว่า auto-chain
   ไป `requirement-writer`/`sync-feature-journey` ระหว่างทาง (เจอ requirement ใหม่) ให้บันทึกไว้
   สำหรับสรุปในข้อ 13 ด้วย เพราะแปลว่า `backlog.md`/`feature-list.md`/`user-journey.md` อาจถูก
   แก้เพิ่มอีกรอบหลังชั้นที่ 1-2 เสร็จไปแล้ว (เป็นเรื่องปกติ ไม่ใช่ข้อผิดพลาด)

8. **สาขา (ข) — feature-list/user-journey ↔ prototype (report-only)**: เรียก subagent
   `prototype-auditor` ผ่าน Agent tool (`run_in_background: false`) **ต้องรอชั้นที่ 2 เสร็จ
   สมบูรณ์ก่อนเสมอ** เช่นกัน (ไม่ต้องรอสาขา (ก) เพราะสามสาขานี้ไม่ขึ้นต่อกัน)

9. **ตรวจสอบผลลัพธ์สาขา (ข)**: ถ้าผลลัพธ์ที่ได้กลับมาแสดงว่า `prototype-auditor` แก้ไข/สร้างไฟล์
   ใดๆ ในโฟลเดอร์ `01-prototypes/` ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที (agent นี้ต้อง report-only
   เท่านั้น)

10. **สาขา (ค) — feature-list/user-journey ↔ เอกสารเชิงเทคนิค (auto-fix ยกเว้น NFR review)**:
    เรียกผ่าน **Skill tool** ด้วย `skill: sync-technical-spec` (ไม่ใช่เรียก subagent แต่ละตัว
    ในสายเทคนิคตรงๆ เพราะ skill นี้จัดลำดับชั้นย่อย 4 ชั้นและมี auto-chain logic ของตัวเองอยู่แล้ว)
    **ต้องรอชั้นที่ 2 เสร็จสมบูรณ์ก่อนเสมอ** (ไม่ต้องรอสาขา (ก)/(ข) เพราะสามสาขานี้ไม่ขึ้นต่อกัน)

11. **ตรวจสอบผลลัพธ์สาขา (ค)**: สุ่มอ่าน `architecture.md`, `api-spec.md`/`db-spec.md`, ไฟล์ใน
    `detailed-design/`, และ `nfr-review.md` จริงอย่างน้อย 1-2 จุด ตรวจว่าไม่มีการระบุชื่อ
    technology/framework/database engine ใดๆ หลุดเข้าไปในเอกสารเหล่านี้ (ต้องยังว่างอยู่ที่
    `technology-stack.md`) ถ้า `sync-technical-spec` รายงานว่า auto-chain ไป
    `requirement-writer`/`sync-feature-journey` ระหว่างทาง ให้บันทึกไว้สำหรับสรุปในข้อ 13 ด้วย
    เช่นเดียวกับข้อ 7

12. **ป้องกันการรายงานซ้ำ**: ถ้าทั้งสาขา (ก) และสาขา (ค) auto-chain ไป `requirement-writer`
    พร้อมกันจากคนละสาเหตุ (เกิดได้เพราะทั้งสองสาขาไม่ขึ้นต่อกัน) ให้รายงานทั้งสองเหตุการณ์แยกกัน
    ชัดเจนในข้อ 13 ไม่ต้องพยายามรวมหรือตัดรายการใดออก

13. **สรุปผลรวมทั้ง pipeline เป็นรายงานเดียว** ให้ผู้ใช้ทราบ แยกตามชั้น:
    - **spec ↔ backlog**: up to date อยู่แล้วหรือแก้ไขอะไรไปบ้าง
    - **backlog ↔ feature-list/user-journey**: up to date อยู่แล้วหรือแก้ไขอะไรไปบ้าง (รวมถึง
      รอบที่สองถ้าถูกแก้ซ้ำจากการ auto-chain ในข้อ 7/11)
    - **feature-list/user-journey ↔ เอกสารทดสอบ**: up to date อยู่แล้วหรือแก้ไขอะไรไปบ้าง
      (acceptance-criteria.md/test-plan.md/test-cases/) รวมถึงความต้องการใหม่ที่ถูก auto-chain
      ไป requirement-writer ให้เอง (ถ้ามี)
    - **feature-list/user-journey ↔ prototype**: up to date หรือล้าสมัยอย่างไรบ้าง (รหัสที่
      ขาดหาย/ล้าสมัย/journey ที่ไม่มีหน้าจอ)
    - **feature-list/user-journey ↔ เอกสารเชิงเทคนิค**: สถานะแต่ละชั้นย่อย (architecture,
      api-spec/db-spec, detailed design) up to date หรือแก้ไขอะไรไปบ้าง รวมถึงผล NFR review
      (จำนวน NFR ที่รองรับแล้ว/บางส่วน/ยังไม่รองรับ พร้อมคำแนะนำว่าควรรันชั้นไหนซ้ำถ้ามีช่องว่าง)
    - จุดที่ subagent/skill ตัวใดถามผู้ใช้ระหว่างทางและคำตอบที่ได้ (ถ้ามี)

14. **ถ้าพบว่า prototype ล้าสมัยหรือยังไม่เคยสร้าง**: ใช้ `AskUserQuestion` ถามผู้ใช้ต่อว่าต้องการ
    จัดการอย่างไร โดยเสนออย่างน้อย 3 ตัวเลือก:
    (1) รัน `build-prototype` ต่อทันทีในเทิร์นเดียวกัน — เรียกผ่าน Skill tool ต่อเลยถ้าผู้ใช้เลือก
    ตัวเลือกนี้ **(แนะนำ)** เพราะปิด pipeline ให้ครบทุกชั้นในคำขอเดียว ไม่ต้องพิมพ์คำสั่งใหม่,
    (2) ไว้ตัดสินใจรันเองทีหลัง — จบงานแค่รายงาน ไม่ทำอะไรต่อ,
    (3) ขอดูรายละเอียดรหัส FR/NFR ที่ขาดหายทั้งหมดก่อนตัดสินใจ — แสดงรายละเอียดที่
    `prototype-auditor` รายงานมาให้อ่านครบก่อน แล้วค่อยถามอีกครั้งว่าจะรันต่อหรือไม่

## ข้อควรระวัง

- **ต้องรันตามลำดับชั้นเสมอ (sequential) ห้ามรันขนานข้ามชั้น** เพราะแต่ละชั้นต้องพึ่งผลลัพธ์
  ที่อัปเดตแล้วของชั้นก่อนหน้าเป็นแหล่งความจริง การรันขนานจะทำให้ชั้นหลังเทียบกับข้อมูลเก่า —
  สาขา (ก) เอกสารทดสอบ, (ข) prototype, และ (ค) เอกสารเชิงเทคนิค เท่านั้นที่ไม่ขึ้นต่อกันเอง
  (รันก่อนหลังกันได้ แต่ทั้งสามต้องรอชั้นที่ 2 เสร็จก่อนเริ่มเสมอ)
- ห้ามข้ามชั้นใดชั้นหนึ่งไปเอง แม้ผู้ใช้จะถามถึงแค่ปัญหาที่ชั้นปลาย (เช่น "test case ตรงไหม",
  "prototype ตรงไหม", หรือ "NFR รองรับหรือยัง") ก็ควรแจ้งผู้ใช้ว่า skill นี้ตรวจทั้งสายงานเสมอ
  เพราะ backlog/feature-list ที่ล้าสมัยจะทำให้ผลตรวจชั้นปลายผิดไปด้วย (เทียบกับแหล่งความจริงที่
  ยังไม่อัปเดต)
- ห้ามข้ามการเรียก subagent/skill แล้วแก้ไฟล์เองตรงๆ ในเทรดหลักไม่ว่าชั้นใด — แต่ละตัวคือแหล่ง
  ความจริงเดียวของกฎการเทียบในชั้นของตัวเอง
- Subagent `prototype-auditor` และ `nfr-reviewer` ไม่มีเครื่องมือที่แก้ไขไฟล์เอกสารต้นทางของตัวเอง
  ได้ (prototype/architecture-api-db-detailed-design ตามลำดับ) ถ้าผลลัพธ์ที่ได้กลับมาพูดถึงการ
  แก้ไขไฟล์เหล่านั้น ให้ถือว่าผิดปกติ หยุดและแจ้งผู้ใช้ทันที
- Skill `sync-test-plan` และ `sync-technical-spec` มี loop guard ของตัวเองอยู่แล้ว (auto-chain
  ได้ไม่เกิน 1 รอบต่อสาขา) ไม่ต้องทำ guard ซ้ำในชั้นนี้ แค่รอผลลัพธ์สุดท้ายกลับมาแล้วตรวจสอบตาม
  ข้อ 7/11
- **เอกสารในสาขา (ค) ต้องไม่ระบุชื่อ technology/framework/database engine ใดๆ** จนกว่า
  `technology-stack.md` จะถูกตัดสินใจแล้วจริง ถ้าพบหลุดเข้าไปในรายงานของ subagent/skill ใด
  ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที
- ถ้า subagent/skill ตัวใดตัวหนึ่งรายงานปัญหาเชิงโครงสร้าง (โฟลเดอร์ที่คาดไว้หาไม่เจอ ฯลฯ) ให้หยุด
  pipeline ทันที ไม่ไปขั้นชั้นถัดไป แล้วรายงานปัญหานั้นให้ผู้ใช้ก่อนเสมอ
- **`sync-phase-plan` และ `condense-docs` ไม่ได้เป็นส่วนหนึ่งของ pipeline นี้โดยเจตนา** —
