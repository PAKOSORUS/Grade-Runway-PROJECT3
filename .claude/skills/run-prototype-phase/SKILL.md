# Run Prototype Phase

Skill นี้เป็น orchestrator สำหรับ "ช่วงที่ 2" ของ pipeline เอกสารของโปรเจกต์ ตามที่ผู้ใช้แบ่งไว้:
prototype เพียงหัวข้อเดียว แต่แยกเป็น 2 sub-step เสมอ (ตรวจสอบก่อน แล้วค่อยตัดสินใจสร้าง/แก้ไข)
เพราะการสร้าง/แก้ prototype ต้องมีขั้นตอนยืนยัน scope กับผู้ใช้แบบโต้ตอบเสมอตามกฎของ
`build-prototype`

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: ใช้ค่าวันที่ปัจจุบันที่มีอยู่ในบริบทของคุณ (รูปแบบ `YYYYMMDD`) เพื่อส่งต่อ
   ให้ subagent/skill ใช้กับไฟล์ log ของวันนี้

2. **sub-step 1 — ตรวจสอบ (report-only)**: เรียก subagent `prototype-auditor` ผ่าน Agent tool
   (`run_in_background: false`) พร้อมบริบทว่านี่คือ session สนทนากับผู้ใช้จริง เพื่อตรวจว่า
   prototype เวอร์ชันล่าสุด (ถ้ามี) ยังครอบคลุมรหัส FR/NFR ทั้งหมดใน `feature-list.md`/
   `user-journey.md` ปัจจุบันหรือไม่

3. **ตรวจสอบผลลัพธ์ sub-step 1**: อ่านรายงานที่ได้จริง ถ้าผลลัพธ์แสดงว่า `prototype-auditor`
   แก้ไข/สร้างไฟล์ใดๆ ในโฟลเดอร์ `01-prototypes/` ให้ถือว่าผิดกฎ (agent นี้ต้อง report-only
   เท่านั้น) หยุดและแจ้งผู้ใช้ทันที

4. **ถ้า up to date อยู่แล้ว หรือยังไม่เคยมี FR/NFR ใดต้องมี prototype**: สรุปผลจบได้เลยที่ข้อ 7
   ไม่ต้องทำ sub-step 2 ต่อ

5. **ถ้าล้าสมัยหรือยังไม่เคยสร้าง**: ใช้ `AskUserQuestion` ถามผู้ใช้ต่อทันทีว่าต้องการจัดการอย่างไร
   โดยเสนออย่างน้อย 3 ตัวเลือก:
   (1) รัน `build-prototype` ต่อทันทีในเทิร์นเดียวกัน **(แนะนำ)** เพราะปิด sub-step ทั้งสองให้ครบ
   ในคำขอเดียว ไม่ต้องพิมพ์คำสั่งใหม่,
   (2) ไว้ตัดสินใจรันเองทีหลัง — จบงานแค่รายงาน ไม่ทำอะไรต่อ,
   (3) ขอดูรายละเอียดรหัส FR/NFR ที่ขาดหายทั้งหมดก่อนตัดสินใจ — แสดงรายละเอียดที่
   `prototype-auditor` รายงานมาให้อ่านครบก่อน แล้วค่อยถามอีกครั้งว่าจะรันต่อหรือไม่

6. **sub-step 2 — สร้าง/แก้ไข (เฉพาะถ้าผู้ใช้เลือกตัวเลือก (1) ในข้อ 5)**: เรียกผ่าน **Skill tool**
   ด้วย `skill: build-prototype` (ไม่เรียก subagent `prototype-writer` ตรงๆ เพราะ skill นี้มี
   logic การถามเวอร์ชันใหม่/แก้ไขเดิมและส่ง context ที่ครบกว่า) ปล่อยให้ skill นี้จัดการขั้นตอน
   ยืนยัน scope กับผู้ใช้เอง อย่ายืนยัน/ตอบแทนผู้ใช้

7. **สรุปผลรวมเป็นรายงานเดียว** แยกตาม sub-step:
   - **ตรวจสอบ**: up to date หรือไม่ รหัส FR/NFR ที่ขาดหาย/ล้าสมัย (ถ้ามี)
   - **สร้าง/แก้ไข** (ถ้าทำ): สร้างเวอร์ชันใหม่หรือแก้เวอร์ชันเดิม โฟลเดอร์ไหน (path เต็ม) ไฟล์ใด
     ถูกสร้าง/แก้ไขบ้าง
   - จุดที่ถาม/รอผู้ใช้ตัดสินใจระหว่างทาง

## ข้อควรระวัง

- **ต้องทำ sub-step 1 ก่อนเสมอ ห้ามข้ามไปเรียก `build-prototype` ตรงๆ** แม้ผู้ใช้จะขอให้
  "อัปเดต prototype" มาตรงๆ ก็ตาม เพราะรายงานความครอบคลุมจาก `prototype-auditor` คือข้อมูลที่
  ช่วยให้ `build-prototype` รู้ scope ที่ขาดหายจริง
- ห้ามข้ามการเรียก subagent/skill แล้วแก้ไฟล์ HTML เองตรงๆ ในเทรดหลัก
- Skill นี้ scope แค่ "ช่วงที่ 2" เท่านั้น — ไม่ย้อนไปแก้ `feature-list.md`/`user-journey.md`/
  `backlog.md` เอง ถ้า `prototype-auditor` หรือ `build-prototype` รายงานว่าเอกสารต้นทางเหล่านี้
  ไม่ตรงกัน ให้แจ้งผู้ใช้ว่าควรรัน `run-requirements-phase` ก่อน แทนการฝืนทำต่อ
- ถ้า subagent/skill ตัวใดตัวหนึ่งรายงานปัญหาเชิงโครงสร้าง (โฟลเดอร์ที่คาดไว้หาไม่เจอ,
  `DESIGN.md` ว่างเปล่า ฯลฯ) ให้หยุดและรายงานผู้ใช้ก่อนเสมอ ไม่ฝืนสร้าง/แก้ prototype ต่อ
