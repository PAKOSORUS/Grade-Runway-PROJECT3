## 1. Scope

### อยู่ในขอบเขต
ฟีเจอร์ 1-22 และ 27 ใน [[../../02-design/feature-list]] ครอบคลุม FR-01..FR-24, FR-28..FR-31, NFR-01..NFR-06 และ NFR-07 (เฉพาะส่วนการสมัครเอง) (รวม 35 รหัส) — ฟีเจอร์ 23-26 (FR-25..27 และ NFR-07 ส่วนที่เหลือ) อยู่ในขอบเขตแต่ยังไม่มีเอกสารทดสอบ ดูหมายเหตุใต้ตารางข้อ 7
- ผู้ใช้เข้าถึงระบบ (REQ-07, ฟีเจอร์ 27): สมัครเองได้เฉพาะ student ห้ามเขียนทับบัญชีเดิม (FR-28), เข้าสู่ระบบและพาไปหน้าตามบทบาท (FR-29), ออกจากระบบและบังคับล็อกอิน (FR-30), บันทึก uid ผู้สร้างรายการ (FR-31), audit การสมัครเอง (NFR-07) — ระดับ กลาง ทั้งหมด (ผู้ใช้ยืนยัน FR-28..31 แล้วเมื่อ 2026-10-28)
- ระบบติดตามและแจ้งเตือนความเสี่ยง (REQ-01): ซิงก์ข้อมูล, แนวโน้ม/ประเมินความเสี่ยง, threshold, แจ้งเตือน, คำแนะนำ, แดชบอร์ด, มุมมองครู, ประวัติ, ความเป็นส่วนตัว
- ช่องแชทแนะนำแนวทางการเรียน (REQ-02): ส่งข้อความ, ตรวจสิทธิ์ผู้ส่ง, คิวรออนุมัติ, ระบุเชิงลบ, อนุมัติ/ปฏิเสธ, แจ้งผู้ส่ง, กันตรวจซ้ำ, audit trail, AI ช่วยวิเคราะห์, การแสดงชื่อผู้ส่ง
- การจัดการซิงก์ล้มเหลว (REQ-03): ใช้ข้อมูลล่าสุดต่อ, แจ้ง admin, ป้ายข้อมูลไม่ทันสมัยแก่ผู้เรียน (FR-19)
- ห้องรวม ปลดล็อกผู้ตรวจ ส่งใหม่หลังถูกปฏิเสธ (REQ-04): ห้องรวม (FR-20) ปลดล็อกอัตโนมัติ/ด้วยมือโดยอาจารย์และ Admin (FR-21) ส่งข้อความใหม่พร้อมเก็บความสัมพันธ์ (FR-22)
- ซิงก์ครั้งแรกล้มเหลวและคำตัดสินหลังล็อกหมดอายุ (REQ-05): ไม่ประเมินความเสี่ยง แจ้ง admin ป้ายรอข้อมูล (FR-23) ปฏิเสธคำตัดสินเมื่อผู้ตัดสินไม่ได้ถือล็อกที่ยังใช้ได้ (ล็อกหมดอายุ ถูกปลดด้วยมือ หรือผู้อื่นล็อกต่อ) แจ้งผู้ตรวจ ข้อความอยู่ในคิว (FR-24)
- หมายเหตุ: ผู้ใช้ยืนยันระดับความสำคัญของ FR-19..FR-22 และ NFR-01..NFR-06 แล้วเมื่อ 2026-10-16 ส่วนระดับของ FR-23 (กลาง) และ FR-24 (สูง) ใน [[../../01-requirements/backlog]] ยังเป็นข้อเสนอรอผู้ใช้ยืนยัน ถ้าเปลี่ยนต้องปรับ AC/test case ให้ตรง

### นอกขอบเขต (ตาม spec)
- REQ-07 (ฟีเจอร์ 27): การยืนยันอีเมล, การรีเซ็ต/เปลี่ยนรหัสผ่าน, ล็อกอินผ่านผู้ให้บริการภายนอก, การป้องกันสมัครซ้ำ/บอต, การผูกบัญชีที่สมัครเองกับผู้เรียนที่นำเข้าซึ่งอีเมลตรงกัน (ยังไม่กำหนด)
- REQ-01: โมเดล ML ทำนายความเสี่ยง, แจ้งเตือนผ่าน LINE/Push, การบันทึกเกรด/เข้าเรียนเองในระบบนี้, การแจ้งผู้ปกครอง
- REQ-02: แชทตอบโต้ real-time, ไฟล์/รูปแนบ, การแจ้งผู้ส่งเมื่อข้อความอนุมัติ, การรายงานข้อความโดยผู้รับ
- REQ-03: กลไก retry ที่ละเอียด, การแจ้งครูที่ปรึกษาเรื่องซิงก์ล้มเหลว
- REQ-04: ผู้รับรายคน, ระบบจับคู่, จำกัดจำนวนครั้งการส่งใหม่
- REQ-05: ให้ผู้ตรวจยืนยันคำตัดสินซ้ำโดยไม่ล็อกใหม่, การเก็บคำตัดสินที่ถูกปฏิเสธไว้เป็นร่าง
- ผลการรันทดสอบจริง (`02-test-result/`) ยังไม่อยู่ในงานนี้ เพราะโปรเจกต์ยังไม่มีซอร์สโค้ด

### ประเด็นที่ spec ยังไม่กำหนด (กระทบการทดสอบ)
ค่า threshold เริ่มต้น, ความถี่ซิงก์/ประเมิน (NFR-03), นิยาม "ผ่านเกณฑ์" (FR-16), นโยบาย PDPA (NFR-01), นโยบายแสดงชื่อผู้ส่ง (NFR-06), SLA การตรวจและระยะเวลาปลดล็อกอัตโนมัติ (FR-21) — test case เขียนแบบไม่ผูกค่า (ใช้ค่าสัญลักษณ์ เช่น T_unlock) และต้องกำหนดก่อนรันทดสอบจริง

คำถามเปิดที่ spec ใหม่บันทึกไว้ (ยังไม่ตัดสิน กระทบ test case):
- FR-19: ข้อมูลไม่ครบ/ผิดรูปแบบ ข้ามเฉพาะเรคอร์ดหรือปฏิเสธทั้งชุด, ช่องทางแจ้ง admin, อายุข้อมูลสูงสุดที่ยังใช้ได้
- FR-21: ผู้ส่งต้องได้รับแจ้งเมื่อข้อความถูกปลดล็อกหรือไม่
- FR-22: ข้อความใหม่ต้องอ้างอิงข้อความเดิมให้ผู้ตรวจเห็นหรือไม่, จำกัดจำนวนครั้งส่งใหม่หรือไม่
- FR-20: assumption ว่านักศึกษาทุกคนรวมผู้ส่งเองเห็นข้อความในห้องรวม (ยังไม่ยืนยัน)
- FR-23: ช่องทางแจ้ง admin (ตามคำถามเปิดของ FR-19)
- FR-24: ผู้ตรวจที่ล็อกต่ออยู่ต้องได้รับแจ้งเมื่อคำตัดสินของผู้ตรวจเดิมถูกปฏิเสธหรือไม่, ช่องทางแจ้งผู้ตรวจ, การบันทึกการปฏิเสธคำตัดสินเป็นเหตุการณ์แยกใน audit trail (assumption ยังไม่ยืนยัน)

ประเด็นที่ปิดแล้ว (ตัดออกจากรายการรอกำหนด): ผู้รับข้อความ = ห้องรวม (FR-20), การส่งใหม่หลังถูกปฏิเสธ = สร้างข้อความใหม่ ข้อความเดิมปิดถาวร (FR-22)

## 2. ประเภทการทดสอบ

| ประเภท | ครอบคลุมรหัส | แนวทาง |
|--------|--------------|--------|
| Functional | FR-01..FR-24 | ทดสอบตาม AC และ happy path ของ [[../../02-design/user-journey]] ทั้ง 7 journey (journey 5 ตรวจและอนุมัติข้อความ และ journey 6 ปลดล็อกด้วยมือ ครอบคลุมกรณีผู้ตัดสินไม่ได้ถือล็อกที่ใช้ได้ของ FR-24) พร้อม negative/edge case |
| Integration / Fault tolerance | FR-01, NFR-03, FR-19, FR-23 | ทดสอบการดึงข้อมูลผ่าน API จาก LMS/ทะเบียน (หรือ stub) การสะท้อนผลในการประเมิน และการจำลองความล้มเหลว (API ล่ม, timeout, ข้อมูลไม่ครบ/ผิดรูปแบบ) รวมซิงก์ครั้งแรกล้มเหลวที่ยังไม่มีข้อมูลเดิม (ไม่ประเมิน ป้ายรอข้อมูล) |
| Security / Access control | NFR-01, NFR-04, FR-08, FR-13, FR-16, FR-20, FR-21, FR-22, FR-24 | ทดสอบสิทธิ์ตามบทบาท การเข้าถึงข้อมูลโดยตรง (เปลี่ยนตัวระบุ) การซ่อนข้อความที่ยังไม่อนุมัติ/ถูกปฏิเสธ/ถูกปลดล็อกกลับคิวในห้องรวมทุกช่องทาง สิทธิ์ปลดล็อกด้วยมือ (อาจารย์/Admin ได้ นักศึกษาไม่ได้) การแก้/อนุมัติข้อความที่ปิดถาวรไม่ได้ และคำตัดสินของผู้ที่ไม่ได้ถือล็อกที่ยังใช้ได้ (ล็อกหมดอายุ ปลดด้วยมือ ผู้อื่นล็อกต่อ รวมการเรียกตรง) ต้องไม่หลุดเป็นอนุมัติ |
| Explainability (ตรวจเนื้อหา) | NFR-02 | ตรวจว่าแจ้งเตือนระบุเงื่อนไขที่เข้าครบทั้งใน-app และอีเมล |
| Data freshness | NFR-03 | ตรวจว่าการประเมินใช้ข้อมูลซิงก์ล่าสุด (ความถี่รอกำหนด) |
| Audit / Traceability | NFR-05, FR-22, FR-24 | ตรวจบันทึกผู้ตรวจ ผล เชิงลบ/ไม่เชิงลบ เหตุผล ความสัมพันธ์ข้อความเดิม-ใหม่หลังถูกปฏิเสธ และคำตัดสินที่ถูกปฏิเสธเพราะผู้ตัดสินไม่ได้ถือล็อกที่ยังใช้ได้ต้องไม่ถูกบันทึกเป็นผลตัดสิน |
| Privacy (policy) | NFR-06 | ตรวจตามนโยบายแสดงชื่อผู้ส่งเมื่อกำหนดแล้ว |
| Concurrency / Timing | FR-18, FR-21, FR-24 | ทดสอบผู้ตรวจสองคนตัดสินพร้อมกัน พฤติกรรมล็อก/ปลดล็อกตามเวลา และการกดตัดสินหลังล็อกหมดอายุ (ใช้ค่าเวลาสัญลักษณ์จนกว่าจะกำหนด) |
| Functional (ฟีเจอร์ 27) | FR-28..FR-31, NFR-07 | ทดสอบตาม AC และ happy path ของ journey "ผู้ใช้ใหม่สมัครบัญชีด้วยตนเอง" และ "ผู้ใช้ทุกบทบาทเข้าสู่ระบบ ใช้งาน และออกจากระบบ" พร้อม edge case (สมัครซ้ำ ข้อมูลเกิน ชื่อว่าง ไม่มีอีเมล บัญชีปิด หลายบทบาท ลงทะเบียนล้มเหลวแล้วลองใหม่) |
| Security / Access control (ฟีเจอร์ 27) | FR-28, FR-29, FR-30, FR-31 | ไม่ให้ยกระดับสิทธิ์ตัวเองตอนสมัคร (บทบาทที่ส่งมาถูกเพิกเฉย) ไม่เขียนทับบัญชีเดิม ปฏิเสธคำสั่งที่ไม่มีหลักฐานตัวตน สิทธิ์ตัดสินจากบทบาทในระบบ ไม่ใช่หน้าที่หน้าเว็บพาไป และ uid ผู้สร้างมาจากตัวตนที่ยืนยันแล้วเท่านั้น |
| Audit / Traceability (ฟีเจอร์ 27) | NFR-07 | ตรวจบันทึกการสมัครเอง (ผู้ทำ เวลา ค่าที่สร้าง) เกิดพร้อมการสร้างบัญชีเท่านั้น และไม่เกิดเมื่อสมัครซ้ำ/ล้มเหลว |
| Regression | ทุกรหัส | รันชุด test case ระดับสูงซ้ำเมื่อมีการแก้ไข |

Performance Testing: ไม่มี NFR ด้านประสิทธิภาพใน backlog จึงไม่กำหนดในแผนนี้ (หากมีเพิ่มภายหลังให้เพิ่มแถว)

## 3. Environment
รอกำหนด tech stack ก่อน — [[../../02-design/02-technical/technology-stack]] ยังไม่ตัดสินใจ จึงไม่ระบุเครื่องมือ/ฐานข้อมูล/เบราว์เซอร์/เฟรมเวิร์กทดสอบ
สิ่งที่ต้องเตรียมในเชิง logical: ข้อมูลทดสอบผู้เรียนหลายแบบ (เสี่ยง/ไม่เสี่ยง/ผู้เรียนใหม่/ค่าขอบ threshold), บัญชีทดสอบทุกบทบาท, ระบบต้นทางจำลองหรือจริง, บัญชีอีเมลรับแจ้งเตือน

## 4. Entry Criteria
- [[acceptance-criteria]] และ test-cases ครบทุกฟีเจอร์ และสอดคล้องกับ [[../../01-requirements/backlog]] ปัจจุบัน
- มีซอร์สโค้ด/build ที่ deploy ในสภาพแวดล้อมทดสอบได้ และกำหนด tech stack แล้ว
- ประเด็นที่ spec ยังไม่กำหนดและกระทบ test case ที่จะรัน (ข้อ 1) ได้รับการยืนยันแล้ว
- ข้อมูลทดสอบและบัญชีทุกบทบาทพร้อม

## 5. Exit Criteria
- test case ระดับสูง (Must have) รันครบและผ่าน 100%
- test case ระดับกลางผ่านอย่างน้อยตามที่ทีมตกลง ข้อบกพร่องระดับร้ายแรง (security/ข้อความที่ไม่อนุมัติรั่วถึงผู้รับ/ข้อมูลผู้เรียนรั่ว) ต้องเป็นศูนย์
- test case ระดับต่ำที่ไม่ผ่านต้องมีบันทึกและแผนแก้
- ผลการรันบันทึกใน `02-test-result/` (ภายหลัง)

## 6. บทบาทผู้ทดสอบ
ผู้สมัครใหม่ (กลายเป็นนักศึกษา) ผู้ใช้หลายบทบาท ผู้ใช้บัญชีปิดใช้งาน และผู้ไม่ล็อกอิน (ฟีเจอร์ 27), ผู้เรียน, ครู/อาจารย์ที่ปรึกษา, ผู้ดูแลระบบ (รวมรับแจ้งซิงก์ล้มเหลว), นักศึกษาผู้ส่ง, นักศึกษาผู้รับ (ผู้อ่านห้องรวม), อาจารย์ (ผู้ตรวจ), Admin (ผู้ตรวจ สิทธิ์เท่าอาจารย์) โดยอาจารย์และ Admin ปลดล็อกข้อความที่ค้างด้วยมือได้ทั้งคู่ และเป็นผู้รับแจ้งเมื่อคำตัดสินถูกปฏิเสธเพราะไม่ได้ถือล็อกที่ยังใช้ได้ — ตามบทบาทใน [[../../02-design/user-journey]]
