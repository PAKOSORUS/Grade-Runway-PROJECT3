## 1. เชื่อมต่อและซิงก์ข้อมูลจากระบบเดิม

#### FR-01 (สูง) — ดึงข้อมูลจากระบบเดิม
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-01]]
- AC-1: Given ตั้งค่าการเชื่อมต่อ LMS/ระบบทะเบียนผ่าน API แล้ว When ระบบซิงก์ข้อมูล Then ระบบดึงข้อมูลเกรด/ผลการเรียน การเข้าเรียน และการส่งงานผ่าน API ได้ครบทั้ง 3 ประเภท
- AC-2: Given ข้อมูลจาก LMS/ทะเบียนถูกดึงมาแล้ว When ระบบประเมินความเสี่ยงของผู้เรียน Then ผลประเมินสะท้อนข้อมูลที่ดึงมา (เปลี่ยนข้อมูลต้นทางแล้วซิงก์ใหม่ ผลประเมินเปลี่ยนตาม)

#### NFR-03 (กลาง) — ความทันสมัยของข้อมูล
ที่มา: [[20261014-01-student-risk-alert#5. Non-functional Requirements|NFR-03]]
- AC-1: Given ระบบซิงก์ข้อมูลตามความถี่ที่กำหนด (ค่าความถี่ยังไม่กำหนดใน spec รอยืนยัน) When ซิงก์รอบใหม่เสร็จ Then การประเมินความเสี่ยงรอบถัดไปใช้ข้อมูลจากการซิงก์ล่าสุด ไม่ใช้ข้อมูลเก่ากว่า

## 2. วิเคราะห์แนวโน้มและประเมินความเสี่ยง

#### FR-02 (สูง) — คำนวณแนวโน้มผลการเรียน
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-02]]
- AC-1: Given ผู้เรียนมีข้อมูลผลการเรียนย้อนหลังเพียงพอ When ระบบคำนวณแนวโน้ม Then ได้ผลแนวโน้มผลการเรียน (เช่น เพิ่มขึ้น/คงที่/ลดลง) ตรงกับข้อมูลย้อนหลังของผู้เรียนคนนั้น
- AC-2: Given ผู้เรียนใหม่ที่ข้อมูลย้อนหลังไม่เพียงพอ When ระบบประเมิน Then ไม่คำนวณแนวโน้มและใช้เฉพาะกฎพื้นฐาน (assumption ใน spec) โดยไม่เกิดข้อผิดพลาด

#### FR-03 (สูง) — ประเมินความเสี่ยงหลายตัวแปร
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-03]]
- AC-1: Given กฎ threshold ของ 4 ตัวแปร (เกรด การเข้าเรียน การส่งงาน แนวโน้ม) When ข้อมูลผู้เรียนเข้าเงื่อนไขตั้งแต่หนึ่งกฎขึ้นไป Then ระบบประเมินว่าผู้เรียนมีความเสี่ยงและระบุกฎที่เข้าเงื่อนไข
- AC-2: Given กฎ threshold ชุดเดียวกัน When ข้อมูลผู้เรียนไม่เข้าเงื่อนไขใดเลย Then ระบบประเมินว่าไม่เสี่ยง

## 3. ตั้งค่า threshold ความเสี่ยง

#### FR-08 (สูง) — ตั้งค่า threshold
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-08]]
- AC-1: Given ผู้ดูแลระบบเปิดหน้าตั้งค่า threshold When เปลี่ยนค่า threshold ของกฎและบันทึก Then การประเมินรอบถัดไปใช้ค่าใหม่ (ผลประเมินของผู้เรียนที่อยู่ใกล้ค่าขอบเปลี่ยนตามค่าใหม่)
- AC-2: Given ผู้ใช้ที่ไม่ใช่ผู้ดูแลระบบ (ผู้เรียนหรือครู/อาจารย์ที่ปรึกษา) When พยายามเข้าหน้าตั้งค่าหรือเรียกใช้งานแก้ threshold Then ระบบปฏิเสธการเข้าถึงและค่า threshold ไม่เปลี่ยน

## 4. แจ้งเตือนความเสี่ยงพร้อมเหตุผล

#### FR-04 (สูง) — แจ้งเตือนความเสี่ยง
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-04]]
- AC-1: Given ผู้เรียนเข้าเงื่อนไขเสี่ยงตามกฎที่ตั้งไว้ When การประเมินเสร็จ Then ผู้เรียนได้รับแจ้งเตือนทั้งใน-app และอีเมล
- AC-2: Given ผู้เรียนไม่เข้าเงื่อนไขเสี่ยง When การประเมินเสร็จ Then ผู้เรียนไม่ได้รับแจ้งเตือนความเสี่ยง

#### NFR-02 (สูง) — ความสามารถอธิบายได้
ที่มา: [[20261014-01-student-risk-alert#5. Non-functional Requirements|NFR-02]]
- AC-1: Given ผู้เรียนได้รับแจ้งเตือนความเสี่ยง When เปิดอ่านแจ้งเตือนทั้งใน-app และอีเมล Then เนื้อหาระบุเหตุผลว่าเข้าเงื่อนไขใด (ตัวแปรและเกณฑ์ที่เข้า) ในช่องทางทั้งสอง

## 5. คำแนะนำการเรียนเฉพาะบุคคล

#### FR-05 (สูง) — คำแนะนำเฉพาะบุคคล
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-05]]
- AC-1: Given ผู้เรียน 2 คนที่มีข้อมูลย้อนหลังต่างกัน When ระบบสร้างคำแนะนำ Then คำแนะนำของแต่ละคนต่างกันและอิงข้อมูลย้อนหลังของคนนั้น ไม่ใช่คำแนะนำทั่วไป
- AC-2: Given ผู้เรียนใหม่ที่ไม่มีข้อมูลย้อนหลังเพียงพอ When ระบบสร้างคำแนะนำ Then ใช้กฎพื้นฐานในการให้คำแนะนำ

## 6. แดชบอร์ดสถานการณ์การเรียนของผู้เรียน

#### FR-06 (กลาง) — แดชบอร์ดผู้เรียน
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-06]]
- AC-1: Given ผู้เรียนล็อกอินแล้ว When เปิดแดชบอร์ด Then เห็นสถานการณ์การเรียนหลายตัวแปร (เกรด การเข้าเรียน การส่งงาน แนวโน้ม) ในหน้าเดียว

## 7. มุมมองครู/อาจารย์ที่ปรึกษา

#### FR-07 (กลาง) — มุมมองครูและอาจารย์ที่ปรึกษา
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-07]]
- AC-1: Given ครู/อาจารย์ที่ปรึกษาล็อกอินแล้ว When เปิดมุมมองผู้เรียนในความดูแล Then เห็นรายชื่อผู้เรียนในความดูแลของตน
- AC-2: Given ครู/อาจารย์ที่ปรึกษาอยู่ในมุมมองรายชื่อ When เลือกผู้เรียนหนึ่งคน Then เห็นสถานการณ์การเรียนและการแจ้งเตือน (พร้อมเหตุผล) ของผู้เรียนคนนั้น

## 8. ประวัติการแจ้งเตือนและคำแนะนำ

#### FR-09 (ต่ำ) — ประวัติการแจ้งเตือนและคำแนะนำ
ที่มา: [[20261014-01-student-risk-alert#4. Functional Requirements|FR-09]]
- AC-1: Given ผู้เรียนเคยได้รับแจ้งเตือนและคำแนะนำมาแล้ว When เปิดประวัติ Then เห็นรายการแจ้งเตือนและคำแนะนำย้อนหลังของตน
- AC-2: Given ครู/อาจารย์ที่ปรึกษาเลือกผู้เรียนในความดูแล When เปิดประวัติของผู้เรียนนั้น Then เห็นประวัติการแจ้งเตือนและคำแนะนำของผู้เรียนคนนั้น

## 9. ความเป็นส่วนตัวและสิทธิ์การมองเห็นข้อมูลการเรียน

#### NFR-01 (สูง) — ความเป็นส่วนตัวของข้อมูลการเรียน
ที่มา: [[20261014-01-student-risk-alert#5. Non-functional Requirements|NFR-01]] (นโยบาย PDPA ยังต้องยืนยัน)
- AC-1: Given ผู้เรียน A ล็อกอินอยู่ When พยายามดูข้อมูลของผู้เรียน B (ผ่าน UI หรือเรียกข้อมูลโดยตรง เช่น เปลี่ยนตัวระบุผู้เรียน) Then ระบบไม่แสดงข้อมูลของ B ให้ A เห็นเฉพาะข้อมูลตน
- AC-2: Given ครู/อาจารย์ที่ปรึกษาล็อกอินอยู่ When เปิดดูผู้เรียน Then เห็นเฉพาะผู้เรียนในความดูแลของตน
- AC-3: Given ผู้เรียนที่ไม่อยู่ในความดูแลของครู/อาจารย์ท่านนั้น When ครูพยายามเข้าถึงข้อมูลผู้เรียนนั้นโดยตรง Then ระบบปฏิเสธการเข้าถึง

## 10. ส่งข้อความแนะนำแนวทางการเรียน

#### FR-10 (สูง) — ส่งข้อความแนะนำแนวทางการเรียน
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-10]]
- AC-1: Given นักศึกษาผู้ผ่านเกณฑ์เปิดช่องแชท When เขียนข้อความแนะนำแนวทางการเรียนและส่ง (ไม่ต้องเลือกผู้รับ เพราะส่งเข้าห้องรวมตาม [[#FR-20 (สูง) — ส่งข้อความเข้าห้องรวม|FR-20]]) Then ระบบรับข้อความและส่งเข้ากระบวนการตรวจ

#### FR-16 (สูง) — ตรวจสิทธิ์ผู้ส่ง
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-16]] (นิยาม "ผ่านเกณฑ์" ยังไม่กำหนด)
- AC-1: Given นักศึกษาที่ไม่ผ่านเกณฑ์ When พยายามส่งข้อความ (ผ่าน UI หรือเรียกส่งโดยตรง) Then ระบบไม่อนุญาตให้ส่งและไม่สร้างข้อความ
- AC-2: Given นักศึกษาที่ผ่านเกณฑ์ When เปิดช่องแชท Then ระบบตรวจสิทธิ์แล้วอนุญาตให้ส่งได้

## 11. คิวรออนุมัติและการซ่อนข้อความจากผู้รับ

#### FR-11 (สูง) — ข้อความเข้าสถานะรออนุมัติ
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-11]]
- AC-1: Given นักศึกษาผู้ส่งส่งข้อความใหม่ When ส่งสำเร็จ Then ข้อความอยู่ในสถานะรออนุมัติและผู้รับ (นักศึกษาอื่นที่เข้าห้องรวมได้ ตาม FR-20) มองไม่เห็น
- AC-2: Given ข้อความอยู่ในสถานะรออนุมัติ When ผู้ตรวจอนุมัติ Then ผู้รับ (นักศึกษาทุกคนในห้องรวม) เห็นข้อความนั้น

#### NFR-04 (สูง) — ความปลอดภัยของเนื้อหา
ที่มา: [[20261014-02-peer-advice-chat#5. Non-functional Requirements|NFR-04]]
- AC-1: Given ข้อความสถานะรออนุมัติ When ผู้รับพยายามเข้าถึงด้วยทางใดก็ตาม (หน้าแชท เรียกข้อมูลโดยตรง การแจ้งเตือน การค้นหา) Then ผู้รับไม่เห็นข้อความหรือเนื้อหาของข้อความ
- AC-2: Given ข้อความถูกปฏิเสธ When ผู้รับพยายามเข้าถึงด้วยทางใดก็ตาม Then ผู้รับไม่เห็นข้อความหรือเนื้อหาของข้อความ

## 12. ตรวจ ระบุเชิงลบ และอนุมัติ/ปฏิเสธข้อความ

#### FR-12 (สูง) — ระบุเชิงลบหรือไม่เชิงลบ
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-12]]
- AC-1: Given ข้อความรออนุมัติที่ผู้ตรวจยังไม่ระบุเชิงลบ/ไม่เชิงลบ When ผู้ตรวจพยายามอนุมัติ Then ระบบไม่อนุญาตให้อนุมัติ
- AC-2: Given ผู้ตรวจระบุเชิงลบหรือไม่เชิงลบให้ข้อความแล้ว When ผู้ตรวจอนุมัติ Then อนุมัติได้

#### FR-13 (สูง) — อนุมัติหรือปฏิเสธข้อความ
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-13]]
- AC-1: Given อาจารย์เข้าคิวข้อความรออนุมัติ When อนุมัติหรือปฏิเสธข้อความ Then ระบบเปลี่ยนสถานะตามผลตัดสิน
- AC-2: Given Admin เข้าคิวข้อความรออนุมัติ When อนุมัติหรือปฏิเสธข้อความ Then ทำได้เหมือนอาจารย์ทุกประการ (สิทธิ์เท่ากัน)
- AC-3: Given ผู้ใช้ที่ไม่ใช่อาจารย์/Admin (เช่น นักศึกษา) When พยายามเข้าคิวตรวจหรืออนุมัติ/ปฏิเสธ Then ระบบปฏิเสธการเข้าถึง

#### FR-14 (สูง) — ผู้ตรวจตัดสินข้อความเชิงลบ
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-14]]
- AC-1: Given ผู้ตรวจระบุข้อความว่าเชิงลบ When บันทึกการระบุ Then ข้อความไม่ถูกปฏิเสธอัตโนมัติและยังรอผู้ตรวจตัดสิน
- AC-2: Given ข้อความเชิงลบรอตัดสิน When ผู้ตรวจเลือกอนุมัติหรือปฏิเสธ Then ระบบทำตามที่ผู้ตรวจตัดสินทั้งสองทาง

## 13. ปฏิเสธพร้อมเหตุผลและแจ้งผู้ส่ง

#### FR-15 (สูง) — ปฏิเสธพร้อมเหตุผลและแจ้งผู้ส่ง
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-15]]
- AC-1: Given ผู้ตรวจเลือกปฏิเสธข้อความ When ไม่กรอกเหตุผล (ว่าง) Then ระบบไม่อนุญาตให้ปฏิเสธ
- AC-2: Given ผู้ตรวจปฏิเสธพร้อมกรอกเหตุผล When ยืนยันการปฏิเสธ Then ผู้ส่งได้รับแจ้งพร้อมเหตุผลเดียวกับที่ผู้ตรวจกรอก

## 14. กันตรวจซ้ำระหว่างผู้ตรวจ

#### FR-18 (กลาง) — กันตรวจซ้ำ
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-18]]
- AC-1: Given ผู้ตรวจ A กำลังตรวจข้อความหนึ่งอยู่ When ผู้ตรวจ B พยายามตัดสินข้อความเดียวกัน Then ระบบไม่อนุญาตให้ B ตัดสิน
- AC-2: Given ข้อความที่ผู้ตรวจคนหนึ่งตัดสินแล้ว When ผู้ตรวจอีกคนพยายามตัดสินซ้ำ Then ระบบไม่อนุญาตและผลตัดสินเดิมไม่เปลี่ยน
- หมายเหตุ: กรณีผู้ตรวจล็อกแล้วไม่ตัดสิน ดูการปลดล็อกที่ [[#FR-21 (กลาง) — ปลดล็อกข้อความที่ผู้ตรวจค้าง|FR-21]] (ฟีเจอร์ 20)

## 15. ประวัติการตรวจข้อความ (audit trail)

#### NFR-05 (สูง) — ความรับผิดชอบ (audit trail)
ที่มา: [[20261014-02-peer-advice-chat#5. Non-functional Requirements|NFR-05]]
- AC-1: Given ผู้ตรวจตัดสินข้อความ (อนุมัติ) When การตัดสินเสร็จ Then ระบบบันทึกว่าผู้ตรวจคนใดตรวจ ผลที่ตัดสิน และการระบุเชิงลบ/ไม่เชิงลบ
- AC-2: Given ผู้ตรวจปฏิเสธข้อความ When การตัดสินเสร็จ Then ระบบบันทึกข้อมูลเหมือน AC-1 พร้อมเหตุผลการปฏิเสธ
- หมายเหตุ: การบันทึกความสัมพันธ์ข้อความเดิม-ใหม่หลังส่งใหม่ ดู [[#FR-22 (กลาง) — ส่งข้อความใหม่หลังถูกปฏิเสธ|FR-22]] AC-4 (ฟีเจอร์ 21)

## 16. AI ช่วยวิเคราะห์เชิงลบ/ไม่เชิงลบ

#### FR-17 (ต่ำ) — AI ช่วยวิเคราะห์เชิงลบหรือไม่เชิงลบ
ที่มา: [[20261014-02-peer-advice-chat#4. Functional Requirements|FR-17]]
- AC-1: Given ผู้ตรวจเลือกใช้ AI ช่วยวิเคราะห์ข้อความ When AI วิเคราะห์เสร็จ Then ระบบแสดงผลเสนอเชิงลบ/ไม่เชิงลบให้ผู้ตรวจยืนยัน และผลยังไม่มีผลจนกว่าผู้ตรวจยืนยัน
- AC-2: Given ผู้ตรวจไม่ใช้ AI When ผู้ตรวจระบุเชิงลบ/ไม่เชิงลบเอง Then ทำงานต่อได้ตามปกติ และผู้ตรวจเป็นผู้ตัดสินขั้นสุดท้ายเสมอแม้ใช้ AI

## 17. การแสดงตัวตนผู้ส่งข้อความ

#### NFR-06 (กลาง) — การแสดงชื่อผู้ส่ง
ที่มา: [[20261014-02-peer-advice-chat#5. Non-functional Requirements|NFR-06]] (นโยบายยังไม่กำหนด เป็นคำถามเปิดใน spec)
- AC-1: Given นโยบายการแสดงชื่อผู้ส่งถูกกำหนดแล้ว (แสดงหรือไม่แสดง) When ผู้รับเปิดอ่านข้อความที่อนุมัติแล้ว Then ข้อความแสดงชื่อผู้ส่งหรือไม่แสดงตรงตามนโยบายที่กำหนด (รอกำหนดนโยบายก่อนรันทดสอบ)

## 18. จัดการซิงก์ล้มเหลว ป้ายข้อมูลไม่ทันสมัย และป้ายรอข้อมูล

#### FR-19 (กลาง) — จัดการซิงก์ล้มเหลว
ที่มา: [[20261016-01-sync-failure-handling#4. Functional Requirements|FR-19]] (ต่อยอดฟีเจอร์ 1; ผู้ใช้ยืนยันระดับความสำคัญแล้วเมื่อ 2026-10-16; ช่องทางแจ้ง admin และอายุข้อมูลสูงสุดที่ยังใช้ได้ยังเป็นคำถามเปิดใน spec)
- AC-1: Given เคยซิงก์สำเร็จอย่างน้อย 1 ครั้ง When ซิงก์รอบใหม่ล้มเหลว (เช่น API ล่ม) Then ระบบไม่หยุดประเมินความเสี่ยง และการประเมินรอบถัดไปใช้ข้อมูลซิงก์ล่าสุดที่สำเร็จ
- AC-2: Given ซิงก์รอบใหม่ล้มเหลว When ระบบตรวจพบความล้มเหลว Then ผู้ดูแลระบบได้รับแจ้ง (ช่องทางรอกำหนด ตาม assumption ใช้ช่องทางแจ้งเตือนในระบบ)
- AC-3: Given ซิงก์ล่าสุดล้มเหลว When ผู้เรียนเปิดแดชบอร์ดหรือหน้าที่แสดงข้อมูลการเรียน Then ผู้เรียนเห็นป้ายว่าข้อมูลไม่ทันสมัย และยังใช้งานส่วนอื่น (เช่น คำแนะนำ) ต่อได้
- AC-4: Given ผู้เรียนเห็นป้ายข้อมูลไม่ทันสมัยอยู่ When ซิงก์รอบถัดไปสำเร็จ Then ป้ายหายไป และการประเมินรอบถัดไปใช้ข้อมูลที่ซิงก์ใหม่
- AC-5: Given สาเหตุความล้มเหลวต่างกัน 3 แบบ (API ล่ม, หมดเวลา, ข้อมูลไม่ครบ/ผิดรูปแบบ) When เกิดขึ้นแบบใดแบบหนึ่ง Then ระบบถือเป็นซิงก์ล้มเหลวและได้ผลตาม AC-1..AC-3 เหมือนกัน (กรณีข้อมูลไม่ครบ/ผิดรูปแบบจะข้ามเฉพาะเรคอร์ดหรือปฏิเสธทั้งชุด รอกำหนด แต่ข้อมูลที่ผิดรูปแบบต้องไม่ถูกนำไปประเมิน)
- AC-6: Given ซิงก์สำเร็จตามปกติ When ผู้เรียนเปิดแดชบอร์ด Then ไม่มีป้ายข้อมูลไม่ทันสมัย และผู้ดูแลระบบไม่ได้รับแจ้งความล้มเหลว

#### FR-23 (กลาง) — ซิงก์ครั้งแรกล้มเหลวโดยไม่มีข้อมูลเดิม
ที่มา: [[20261016-03-first-sync-failure-and-expired-lock-decision#4. Functional Requirements|FR-23]] (ต่อยอด FR-19; ระดับความสำคัญ "กลาง" เป็นข้อเสนอรอผู้ใช้ยืนยัน; ช่องทางแจ้ง admin ยังเป็นคำถามเปิดใน spec)
- AC-1: Given ยังไม่เคยมีการซิงก์สำเร็จเลย (ซิงก์ครั้งแรก) When ซิงก์ล้มเหลว Then ระบบไม่สร้างผลประเมินความเสี่ยงของผู้เรียนใดและไม่ส่งแจ้งเตือนความเสี่ยง (ทั้งใน-app และอีเมล)
- AC-2: Given ซิงก์ครั้งแรกล้มเหลวโดยไม่มีข้อมูลเดิม When ระบบตรวจพบความล้มเหลว Then ผู้ดูแลระบบได้รับแจ้ง (ช่องทางรอกำหนด ตาม assumption ของ FR-19)
- AC-3: Given ซิงก์ครั้งแรกล้มเหลวโดยไม่มีข้อมูลเดิม (รวมกรณีล้มเหลวต่อเนื่องหลายรอบโดยยังไม่เคยสำเร็จ) When ผู้เรียนเปิดแดชบอร์ดหรือหน้าที่แสดงข้อมูลการเรียน Then ผู้เรียนเห็นป้ายรอข้อมูลและไม่เห็นผลประเมินใดๆ
- AC-4: Given ผู้เรียนเห็นป้ายรอข้อมูลอยู่ When ซิงก์สำเร็จครั้งแรก Then ป้ายรอข้อมูลหาย และการประเมินความเสี่ยงทำงานตามปกติ
- AC-5: Given เคยซิงก์สำเร็จอย่างน้อย 1 ครั้งแล้ว When ซิงก์รอบใหม่ล้มเหลว Then ผู้เรียนเห็นป้ายข้อมูลไม่ทันสมัยตาม FR-19 (ไม่ใช่ป้ายรอข้อมูล) และการประเมินใช้ข้อมูลล่าสุดที่สำเร็จ

## 19. ห้องรวมแสดงข้อความที่อนุมัติแล้ว

#### FR-20 (สูง) — ส่งข้อความเข้าห้องรวม
ที่มา: [[20261016-02-peer-chat-recipients-lock-resubmit#4. Functional Requirements|FR-20]] (ต่อยอดฟีเจอร์ 10-11; ผู้ใช้ยืนยันระดับความสำคัญแล้วเมื่อ 2026-10-16; assumption ว่า "นักศึกษาทุกคน" รวมผู้ส่งเอง ยังไม่ยืนยัน)
- AC-1: Given นักศึกษาผู้ผ่านเกณฑ์เปิดช่องแชท When เขียนและส่งข้อความแนะนำ Then ข้อความถูกส่งเข้าห้องรวมเดียวโดยไม่ต้องเลือกผู้รับ และอยู่ในสถานะรออนุมัติ
- AC-2: Given ข้อความในห้องรวมได้รับการอนุมัติ When นักศึกษาคนใดในระบบเปิดห้องรวม Then เห็นข้อความนั้นทุกคน
- AC-3: Given ระบบทำงานตามปกติ When ตรวจหน้าส่งข้อความและการรับข้อความ Then ไม่มีการเลือกผู้รับรายคนหรือการจับคู่ผู้ส่ง-ผู้รับ และการอนุมัติไม่จำกัดการมองเห็นเฉพาะนักศึกษาบางคน

#### NFR-04 (สูง) — ความปลอดภัยของเนื้อหา (บริบทห้องรวม)
ที่มา: [[20261014-02-peer-advice-chat#5. Non-functional Requirements|NFR-04]] ที่ [[20261016-02-peer-chat-recipients-lock-resubmit#5. Non-functional Requirements|REQ-04]] ระบุว่า FR-20 ต้องเป็นไปตาม (AC ชุดแรกของ NFR-04 อยู่ที่ฟีเจอร์ 11)
- AC-1: Given ข้อความรออนุมัติ When นักศึกษาคนใดก็ตามในห้องรวม (รวมนักศึกษาที่ไม่ใช่ผู้ส่ง) พยายามเข้าถึงด้วยทางใดก็ตาม (เปิดห้อง เรียกข้อมูลโดยตรง การแจ้งเตือน การค้นหา) Then ไม่เห็นข้อความหรือเนื้อหาของข้อความ
- AC-2: Given ข้อความถูกปฏิเสธ When นักศึกษาคนใดก็ตามพยายามเข้าถึงในห้องรวมด้วยทางใดก็ตาม Then ไม่เห็นข้อความหรือเนื้อหาของข้อความ
- AC-3: Given ข้อความที่ถูกปลดล็อกกลับเข้าคิวตาม [[#FR-21 (กลาง) — ปลดล็อกข้อความที่ผู้ตรวจค้าง|FR-21]] When นักศึกษาคนใดเปิดห้องรวมหรือเข้าถึงโดยตรง Then ไม่เห็นข้อความนั้นจนกว่าจะอนุมัติ

## 20. ปลดล็อกข้อความที่ผู้ตรวจค้าง

#### FR-21 (กลาง) — ปลดล็อกข้อความที่ผู้ตรวจค้าง
ที่มา: [[20261016-02-peer-chat-recipients-lock-resubmit#4. Functional Requirements|FR-21]] (ต่อยอดฟีเจอร์ 14; ผู้ใช้ยืนยันระดับความสำคัญแล้วเมื่อ 2026-10-16 และยืนยันว่าอาจารย์และ Admin ปลดล็อกด้วยมือได้; ระยะเวลาปลดล็อกอัตโนมัติ/SLA ยังไม่กำหนดค่า — เขียนแบบไม่ผูกค่า)
- AC-1: Given ผู้ตรวจ A ล็อกข้อความ M แล้วไม่ตัดสินจนครบเวลาปลดล็อกที่ตั้งไว้ (ค่ารอกำหนด) When ครบเวลา Then ระบบปลดล็อก M อัตโนมัติ M กลับเข้าคิวรออนุมัติ และผู้ตรวจอื่นล็อกตรวจต่อได้
- AC-2: Given ผู้ตรวจ A ล็อก M อยู่และยังไม่ครบเวลา When ผู้ตรวจอื่นพยายามตัดสิน M หรือเมื่อ A ตัดสินทันเวลา Then ผู้ตรวจอื่นยังตัดสินไม่ได้ (ล็อกมีผล) และถ้า A ตัดสินทันเวลา ผลตัดสินมีผลตามปกติโดย M ไม่ถูกปลดล็อก
- AC-3: Given M ถูกผู้ตรวจล็อกค้าง When Admin เลือกปลดล็อกด้วยมือ Then M กลับเข้าคิวรออนุมัติทันที และผู้ตรวจอื่นล็อกตรวจต่อได้
- AC-4: Given M ถูกปลดล็อก (อัตโนมัติหรือด้วยมือ) When ตรวจสถานะและประวัติ Then M ยังอยู่สถานะรออนุมัติ การปลดล็อกไม่ถือเป็นการตัดสิน (ไม่มีผลอนุมัติ/ปฏิเสธ และผู้ส่งไม่ได้รับแจ้งการปฏิเสธ)
- AC-5: Given M ถูกปลดล็อก (อัตโนมัติหรือด้วยมือ) When นักศึกษาคนใดพยายามเข้าถึง M Then ไม่เห็น M (ไม่หลุดถึงผู้รับ ตาม NFR-04)
- AC-6: Given ผู้ใช้บทบาทนักศึกษา When พยายามปลดล็อกข้อความที่ค้าง (ผ่าน UI หรือเรียกโดยตรง) Then ระบบปฏิเสธและ M ยังคงสถานะเดิม
- AC-7: Given ค่าเวลาปลดล็อกอัตโนมัติถูกเปลี่ยน (ผู้มีสิทธิ์ตั้งค่าตามที่ออกแบบ) When มีการล็อกครั้งถัดไป Then การปลดล็อกอัตโนมัติใช้ค่าใหม่
- AC-8: Given M ถูกผู้ตรวจล็อกค้าง When อาจารย์ (สิทธิ์เท่า Admin) เลือกปลดล็อกด้วยมือ Then M กลับเข้าคิวรออนุมัติทันทีเหมือน AC-3 ทุกประการ และผู้ตรวจอื่นล็อกตรวจต่อได้
- หมายเหตุ: ผู้ปลดล็อกด้วยมือได้คืออาจารย์และ Admin เท่านั้น (นักศึกษาปลดไม่ได้ ตาม AC-6) กรณีผู้ตรวจกดตัดสินหลังล็อกถูกปลด (อัตโนมัติหรือด้วยมือ) ดู [[#FR-24 (สูง) — ปฏิเสธคำตัดสินเมื่อผู้ตัดสินไม่ได้ถือล็อกที่ยังใช้ได้|FR-24]] (ฟีเจอร์ 22)

## 21. ส่งข้อความใหม่หลังถูกปฏิเสธ

#### FR-22 (กลาง) — ส่งข้อความใหม่หลังถูกปฏิเสธ
ที่มา: [[20261016-02-peer-chat-recipients-lock-resubmit#4. Functional Requirements|FR-22]] (ต่อยอดฟีเจอร์ 13 และ 15, NFR-05; ผู้ใช้ยืนยันระดับความสำคัญแล้วเมื่อ 2026-10-16; การจำกัดจำนวนครั้งส่งใหม่และการแสดงข้อความเดิมให้ผู้ตรวจเห็นยังเป็นคำถามเปิด)
- AC-1: Given ข้อความ M ถูกปฏิเสธแล้ว When ผู้ส่งพยายามแก้ไขเนื้อหา หรือผู้ใดพยายามอนุมัติ/เปลี่ยนสถานะ M ภายหลัง (ผ่าน UI หรือเรียกโดยตรง) Then ระบบไม่อนุญาต M ปิดถาวรและคงสถานะปฏิเสธ
- AC-2: Given ผู้ส่งได้รับแจ้งว่า M ถูกปฏิเสธ When ผู้ส่งสร้างข้อความใหม่ M2 Then M2 เป็นข้อความใหม่ที่เข้าสถานะรออนุมัติและผู้รับมองไม่เห็น
- AC-3: Given M2 ถูกสร้างหลัง M ถูกปฏิเสธ When M2 เข้าสู่การตรวจ Then M2 ต้องผ่านการตรวจใหม่ทั้งหมด (ระบุเชิงลบ/ไม่เชิงลบ และตัดสินอนุมัติ/ปฏิเสธ) ไม่ถูกอนุมัติโดยอัตโนมัติแม้เนื้อหาเหมือนเดิม
- AC-4: Given M2 ถูกสร้างหลัง M ถูกปฏิเสธ When ตรวจ audit trail Then มีบันทึกความสัมพันธ์ M ↔ M2 และบันทึกการปฏิเสธเดิมของ M (ผู้ตรวจ ผล เชิงลบ/ไม่เชิงลบ เหตุผล) ไม่เปลี่ยน

## 22. ปฏิเสธคำตัดสินเมื่อผู้ตัดสินไม่ได้ถือล็อกที่ยังใช้ได้

ฟีเจอร์: [[../../02-design/feature-list#22. ปฏิเสธคำตัดสินเมื่อผู้ตัดสินไม่ได้ถือล็อกที่ยังใช้ได้|feature-list ข้อ 22]] | journey: [[../../02-design/user-journey#Journey: อาจารย์/Admin ตรวจและอนุมัติข้อความ|อาจารย์/Admin ตรวจและอนุมัติข้อความ]] (ขั้น 3-6), [[../../02-design/user-journey#Journey: อาจารย์/Admin ปลดล็อกข้อความที่ผู้ตรวจค้างด้วยมือ|อาจารย์/Admin ปลดล็อกข้อความที่ผู้ตรวจค้างด้วยมือ]] (ขั้น 5-6)

#### FR-24 (สูง) — ปฏิเสธคำตัดสินเมื่อผู้ตัดสินไม่ได้ถือล็อกที่ยังใช้ได้
ที่มา: [[20261016-03-first-sync-failure-and-expired-lock-decision#4. Functional Requirements|FR-24]] (ต่อยอดฟีเจอร์ 14 และ 20; ต้องเป็นไปตาม NFR-04 และ NFR-05; ขอบเขตขยายเมื่อ 2026-10-16 เป็น "ผู้ตัดสินไม่ได้ถือล็อกที่ยังใช้ได้" ครอบคลุม (ก) ล็อกหมดอายุอัตโนมัติ (ข) ถูกอาจารย์/Admin ปลดด้วยมือตาม FR-21 (ค) ผู้ตรวจอื่นล็อกต่อแล้ว; ระดับความสำคัญ "สูง" เป็นข้อเสนอรอผู้ใช้ยืนยัน; ช่องทางแจ้งผู้ตรวจ และการแจ้งผู้ตรวจที่ล็อกต่ออยู่ ยังเป็นคำถามเปิดใน spec; ระยะเวลาปลดล็อกใช้ค่าสัญลักษณ์ T_unlock)
- AC-1: Given ผู้ตรวจ A ล็อกข้อความ M แล้วล็อกถูกปลดอัตโนมัติ (ครบ T_unlock) ไปแล้ว When A กดตัดสิน M (อนุมัติหรือปฏิเสธ) Then ระบบปฏิเสธคำตัดสินนั้น ไม่บันทึกเป็นการตัดสิน และสถานะของ M ไม่เปลี่ยน
- AC-2: Given คำตัดสินของ A ถูกปฏิเสธเพราะ A ไม่ได้ถือล็อกที่ยังใช้ได้ (ตาม AC-1, AC-6 หรือ AC-8) When ระบบปฏิเสธ Then A ได้รับแจ้งว่าคำตัดสินไม่ถูกบันทึกเพราะไม่ได้ถือล็อกที่ยังใช้ได้ (ล็อกหมดอายุหรือถูกปลดล็อก; ช่องทางรอกำหนด)
- AC-3: Given คำตัดสินของ A ถูกปฏิเสธตาม AC-1 When ตรวจสถานะ M และห้องรวม Then M อยู่ในคิวรออนุมัติ ไม่ปรากฏในห้องรวม และนักศึกษาคนใดเข้าถึงไม่ได้ทุกช่องทาง (ตาม NFR-04) แม้ A กดอนุมัติ
- AC-4: Given คำตัดสินของ A ถูกปฏิเสธตาม AC-1 When ตรวจประวัติการตรวจของ M Then ไม่มีบันทึกผลอนุมัติ/ปฏิเสธจากคำตัดสินนั้น และผู้ส่งไม่ได้รับแจ้งการปฏิเสธข้อความ (การบันทึกการปฏิเสธคำตัดสินเป็นเหตุการณ์แยกใน audit trail เป็น assumption ใน spec ยังไม่ยืนยัน ตาม NFR-05)
- AC-5: Given A ไม่ได้ถือล็อกที่ยังใช้ได้ของ M ไม่ว่าสาเหตุใด (ล็อกหมดอายุ ถูกปลดด้วยมือ หรือผู้อื่นล็อกต่อ) When A ส่งคำสั่งตัดสิน M โดยตรง (ไม่ผ่าน UI เช่น เรียกคำสั่งอนุมัติซ้ำ หรือใช้หน้าจอเดิมที่เปิดค้างไว้) Then ระบบปฏิเสธเช่นเดียวกับ AC-1..AC-3 และ M ไม่ถูกอนุมัติ
- AC-6: Given ล็อกของ A หมดอายุและผู้ตรวจ B ล็อก M ต่อแล้ว When A กดตัดสิน M Then คำตัดสินของ A ถูกปฏิเสธและแจ้ง A ล็อกและการตัดสินของ B ไม่ได้รับผลกระทบ (การแจ้ง B ยังเป็นคำถามเปิดใน spec ไม่ระบุใน AC นี้)
- AC-7: Given M ถูกปฏิเสธคำตัดสินของ A และกลับอยู่ในคิว When ผู้ตรวจ B ล็อก ระบุเชิงลบ/ไม่เชิงลบ และอนุมัติ M ภายในล็อกที่ยังใช้ได้ Then คำตัดสินของ B มีผลตามปกติ และ M ถูกอนุมัติได้เฉพาะโดยผู้ตรวจที่ถือล็อกที่ยังใช้ได้เท่านั้น
- AC-8: Given ผู้ตรวจ A ล็อก M แล้วถูกอาจารย์/Admin ปลดล็อกด้วยมือตาม [[#FR-21 (กลาง) — ปลดล็อกข้อความที่ผู้ตรวจค้าง|FR-21]] (ยังไม่ครบ T_unlock) When A กดตัดสิน M ภายหลัง (อนุมัติหรือปฏิเสธ) Then ระบบปฏิเสธคำตัดสินและแจ้ง A เหมือนกรณีล็อกหมดอายุ (AC-1..AC-4 ทุกข้อ: ไม่บันทึกเป็นการตัดสิน M อยู่ในคิวไม่หลุดถึงนักศึกษา ผู้ส่งไม่ได้รับแจ้งการปฏิเสธ)
- AC-9: Given ผู้ตรวจที่ไม่ได้ถือล็อกที่ยังใช้ได้ของ M ไม่ว่าด้วยสาเหตุใด (รวมผู้ที่ไม่เคยล็อก M เลย) When พยายามให้ M ถูกอนุมัติ (ผ่าน UI หรือส่งคำสั่งตรงโดยไม่ผ่านหน้าจอ) Then M ไม่ถูกอนุมัติ และ M ถูกอนุมัติได้ก็ต่อเมื่อผู้ตรวจที่ถือล็อกที่ยังใช้ได้เป็นผู้ตัดสินเท่านั้น

## 27. สมัครบัญชี เข้าสู่ระบบ ออกจากระบบ และบันทึกผู้สร้างรายการ

ฟีเจอร์: [[../../02-design/feature-list#27. สมัครบัญชี เข้าสู่ระบบ ออกจากระบบ และบันทึกผู้สร้างรายการ|feature-list ข้อ 27]] | journey: [[../../02-design/user-journey#Journey: ผู้ใช้ใหม่สมัครบัญชีด้วยตนเอง|ผู้ใช้ใหม่สมัครบัญชีด้วยตนเอง]], [[../../02-design/user-journey#Journey: ผู้ใช้ทุกบทบาทเข้าสู่ระบบ ใช้งาน และออกจากระบบ|ผู้ใช้ทุกบทบาทเข้าสู่ระบบ ใช้งาน และออกจากระบบ]] | spec: [[../../01-requirements/01-spec/20261027-01-self-registration-and-login|REQ-07]] | detailed design: [[../../02-design/02-technical/detailed-design/self-registration-and-login|self-registration-and-login]]
ระดับความสำคัญของ FR-28..31 = กลาง (ผู้ใช้ยืนยันแล้วเมื่อ 2026-10-28) ดึงจาก [[../../01-requirements/backlog|Backlog]] ส่วน NFR-07 (กลาง) ใช้ NFR เดิมโดยขยายให้ครอบคลุมการสมัครเอง (AC ของ NFR-07 ในหัวข้อนี้ครอบคลุมเฉพาะการสมัครเอง) ประเด็นเปิดของ spec (ยังไม่มี AC): การผูกบัญชีที่สมัครเองกับผู้เรียนที่นำเข้าซึ่งอีเมลตรงกัน, การยืนยันอีเมล/รีเซ็ตรหัสผ่าน (out of scope)

#### FR-28 (กลาง) — สมัครบัญชีด้วยตนเอง
ที่มา: [[20261027-01-self-registration-and-login#4. Functional Requirements|FR-28]]
- AC-1: Given ผู้ใช้ใหม่ที่ยังไม่มีบัญชีผู้ใช้ฝั่งระบบ When สมัครด้วยชื่อ อีเมล และรหัสผ่านสำเร็จ (ไม่มีช่องเลือกบทบาท) Then ระบบสร้างบัญชีผู้ใช้ของ uid นั้นด้วยบทบาท student เพียงบทบาทเดียว สถานะใช้งาน แหล่งที่มา = สมัครเอง และผลการสมัครคือสร้างบัญชีใหม่
- AC-2: Given ผู้สมัครส่งค่าบทบาท/สถานะ/แหล่งที่มา/uid มาเกินจากชื่อ (เช่น พยายามส่ง admin) When เรียกสร้างบัญชี Then ค่าเหล่านั้นถูกเพิกเฉยโดยไม่เกิด error ได้บทบาท student เท่านั้น และ uid/อีเมลมาจากหลักฐานตัวตนที่ยืนยันแล้ว
- AC-3: Given uid นั้นมีบัญชีผู้ใช้อยู่แล้ว (ไม่ว่ามาจากการสมัครเอง การนำเข้า หรือ Admin สร้าง และไม่ว่าสถานะใช้งานหรือปิดใช้งาน) When สมัครซ้ำ/เรียกสร้างซ้ำ Then ข้อมูลเดิม (ชื่อ อีเมล บทบาท สถานะ แหล่งที่มา) ไม่ถูกเขียนทับ ผลการสมัครคือมีบัญชีอยู่แล้ว (ไม่ใช่ error) ไม่ส่งข้อมูลบัญชีเดิมกลับ
- AC-4: Given ผู้สมัครกรอกชื่อ-นามสกุลว่าง When เรียกสร้างบัญชี Then ระบบปฏิเสธ (ข้อมูลไม่ถูกต้อง) ไม่สร้างบัญชี บทบาท หรือบันทึก audit ใดๆ
- AC-5: Given หลักฐานตัวตนที่ยืนยันแล้วไม่มีอีเมล (ระบบไม่รับอีเมลจากค่าที่ผู้ใช้ส่ง) When เรียกสร้างบัญชี Then ระบบปฏิเสธ (ข้อมูลไม่ถูกต้อง) ไม่สร้างสิ่งใด
- AC-6: Given ไม่มีหลักฐานตัวตนที่ตรวจได้ (ยังไม่ล็อกอิน/หมดอายุ) When เรียกสร้างบัญชี Then ระบบปฏิเสธเพราะยังไม่ยืนยันตัวตน ไม่สร้างสิ่งใด และหน้าเว็บพากลับหน้า login
- AC-7: Given สร้างตัวตนสำเร็จแต่การสร้างบัญชีฝั่งระบบไม่สำเร็จ (ล้มเหลวกลางทาง/ขาดการเชื่อมต่อ) When ลองสร้างบัญชีใหม่ (เช่น ตอนล็อกอินครั้งถัดไปที่ระบบแจ้งว่าไม่พบบัญชี) Then ไม่มีบัญชี/บทบาท/audit ค้างครึ่งเดียวจากครั้งแรก การลองใหม่สร้างบัญชีได้สำเร็จหรือได้ผลมีบัญชีอยู่แล้ว โดยไม่เกิดบัญชีหรือ audit ซ้ำ และถ้ามีคำสั่งสมัครของ uid เดียวกันซ้อนกัน สร้างใหม่ได้ไม่เกิน 1 ครั้ง
- AC-8: Given นักศึกษาที่เพิ่งสมัครเอง (ยังไม่มีผลประเมินเกณฑ์ผู้ผ่านเกณฑ์ และยังไม่มีครู/อาจารย์ที่ปรึกษา) When พยายามส่งข้อความแนะนำ Then ระบบไม่อนุญาตเพราะยังไม่ผ่านเกณฑ์ตาม [[#FR-16 (สูง) — ตรวจสิทธิ์ผู้ส่ง|FR-16]]/FR-27 จนกว่าจะประเมินผ่าน การสมัครไม่ให้สิทธิ์เพิ่ม

#### FR-29 (กลาง) — เข้าสู่ระบบและพาไปหน้าตามบทบาท
ที่มา: [[20261027-01-self-registration-and-login#4. Functional Requirements|FR-29]]
- AC-1: Given ผู้ใช้ที่มีบัญชีสถานะใช้งาน When เข้าสู่ระบบด้วยอีเมล/รหัสผ่านสำเร็จ Then admin ไปหน้า Admin, อาจารย์ (ผู้ตรวจ) ไปหน้าผู้ตรวจ, นักศึกษาและครู/อาจารย์ที่ปรึกษาไปแดชบอร์ด
- AC-2: Given ผู้ใช้มีหลายบทบาท When เข้าสู่ระบบ Then ไปหน้าตามลำดับ Admin → อาจารย์ → อื่นๆ (เช่น admin+อาจารย์ ไปหน้า Admin, อาจารย์+นักศึกษา ไปหน้าผู้ตรวจ, ครูที่ปรึกษา+นักศึกษา ไปแดชบอร์ด)
- AC-3: Given บัญชีผู้ใช้ถูกปิดใช้งาน When พยายามเข้าสู่ระบบ Then เข้าใช้งานไม่ได้ ไม่ถูกพาไปหน้าใดตามบทบาท และ operation อื่นของบัญชีนั้นถูกปฏิเสธเช่นกัน
- AC-4: Given ผู้ใช้เข้าสู่ระบบแล้ว When หน้าเว็บอ่านโปรไฟล์ของตน Then ได้เฉพาะชื่อ รายการบทบาทที่ใช้งาน และสถานะของตนเอง (อ่านอย่างเดียว) ไม่มีช่องระบุผู้ใช้อื่น และไม่ได้อีเมล รหัสในระบบเดิม หรือแหล่งที่มา
- AC-5: Given ผู้ใช้ไม่มีบทบาทใช้งานเลย When เข้าสู่ระบบและอ่านโปรไฟล์ Then ได้รายการบทบาทว่าง ไม่มีหน้าปลายทางตามบทบาท และ operation ที่ต้องมีบทบาทถูกปฏิเสธ (ไม่มีสิทธิ์)
- AC-6: Given หน้าเว็บเลือกหน้าตามบทบาทที่อ่านได้ When ผู้ใช้พยายามเรียก operation ของบทบาทอื่นโดยตรง (เช่น นักศึกษาเรียกคำสั่งของ Admin) Then สิทธิ์ตัดสินจากบทบาทในระบบเท่านั้น ไม่ใช่จากหน้าที่หน้าเว็บพาไป และคำสั่งถูกปฏิเสธ

#### FR-30 (กลาง) — ออกจากระบบและบังคับล็อกอิน
ที่มา: [[20261027-01-self-registration-and-login#4. Functional Requirements|FR-30]]
- AC-1: Given ผู้ใช้ล็อกอินอยู่ที่หน้าใดก็ตาม (Admin ผู้ตรวจ แดชบอร์ด) When กดปุ่มออกจากระบบ Then ทุกหน้ามีปุ่มนี้ เซสชันสิ้นสุด และถูกพาไปหน้า login
- AC-2: Given ผู้ใช้ออกจากระบบแล้ว When เข้าหน้าภายใน (ย้อนกลับหรือพิมพ์ที่อยู่หน้าโดยตรง) Then ถูกพาไปหน้า login ไม่เห็นข้อมูลภายใน
- AC-3: Given ผู้ที่ยังไม่ล็อกอิน When เข้าหน้า Admin/ผู้ตรวจ/แดชบอร์ดโดยตรง Then ถูกพาไปหน้า login
- AC-4: Given request ที่ไม่มีหลักฐานตัวตนที่ยืนยันแล้ว When เรียก operation ที่ต้องยืนยันตัวตน Then ระบบปฏิเสธเพราะยังไม่ยืนยันตัวตน

#### FR-31 (กลาง) — บันทึกผู้สร้างรายการ
ที่มา: [[20261027-01-self-registration-and-login#4. Functional Requirements|FR-31]]
- AC-1: Given ผู้ใช้ที่ยืนยันตัวตนแล้ว When สร้างรายการใหม่ (เช่น สมัครบัญชี ส่งข้อความ สร้างบัญชี/ความสัมพันธ์โดย Admin นำเข้าข้อมูล) Then รายการนั้นบันทึก uid ของผู้สร้างตรงกับผู้เรียก
- AC-2: Given ผู้ใช้ส่งค่า uid/ผู้สร้าง/ผู้ทำ ของคนอื่นมาในคำสั่ง When สร้างรายการ Then ค่าที่ส่งมาถูกเพิกเฉย uid ผู้สร้างมาจากตัวตนที่ยืนยันแล้วของผู้เรียกเท่านั้น ระบุ uid อื่นแทนไม่ได้
- AC-3: Given นักศึกษาส่งข้อความแชท When ตรวจข้อความที่สร้าง Then ผู้ส่ง (senderId) เท่ากับ uid ผู้เรียก ถือว่าเข้าข้อกำหนดนี้ และส่งในนามผู้อื่นไม่ได้

#### NFR-07 (กลาง) — audit trail การสมัครเอง (บริบทฟีเจอร์ 27)
ที่มา: [[20261017-01-user-role-advisor-eligibility-management#5. Non-functional Requirements|NFR-07]] (ขยายเมื่อ 2026-10-27 ให้ครอบคลุมการสมัครเองตาม [[20261027-01-self-registration-and-login#6. Business Rules|REQ-07]]; AC นี้ครอบคลุมเฉพาะการสมัครเอง AC ของ audit การเปลี่ยนอื่นอยู่นอกขอบเขตเอกสารฉบับนี้ ดูหมายเหตุใน test-plan)
- AC-1: Given ผู้ใช้สมัครเองสำเร็จ (สร้างบัญชีใหม่) When ตรวจประวัติการเปลี่ยนบัญชี Then มีบันทึกประเภทบัญชี การกระทำ = สมัครเอง ผู้ทำ = uid ผู้สมัคร เป้าหมาย = uid ผู้สมัครเอง เวลา และค่าที่สร้าง (บทบาท student สถานะใช้งาน แหล่งที่มา = สมัครเอง ค่าก่อนว่าง)
- AC-2: Given การสมัครที่ไม่สร้างบัญชี (สมัครซ้ำจนได้มีบัญชีอยู่แล้ว ชื่อว่าง ไม่มีอีเมล ไม่มีหลักฐานตัวตน หรือล้มเหลว) When ตรวจประวัติ Then ไม่มีบันทึกการสมัครเองเพิ่ม
- AC-3: Given การสมัครเองหนึ่งครั้ง When ตรวจบัญชี บทบาท และบันทึก audit Then ทั้งสามเกิดพร้อมกันหรือไม่เกิดเลย (ไม่มีบัญชีที่ไม่มี audit และไม่มี audit ที่ไม่มีบัญชี)
