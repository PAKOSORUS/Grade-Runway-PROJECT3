## เริ่ม Phase 4: วิเคราะห์ความเสี่ยง แจ้งเตือนในแอป คำแนะนำ และมุมมองผู้ใช้ (สาขา `claude/close-phase3-leftovers`)
- `functions/lib/risk.js`: `evaluate` (ฟังก์ชันล้วน) คำนวณแนวโน้ม 4 แบบ (ดีขึ้น/ทรงตัว/ลดลง/ข้อมูลไม่พอ) และประเมิน 4 ตัวแปรกับกฎ threshold, `recommend` สร้างคำแนะนำจากกฎที่เข้า (ผู้เรียนใหม่ข้อมูลไม่พอ = กฎพื้นฐานเท่านั้น), `shouldNotify` ตามทาง B (แจ้งเมื่อไม่เสี่ยง→เสี่ยง หรือชุดกฎที่เข้าเปลี่ยน), `assessAll` (OP-07) อ่านชุด threshold ครั้งเดียวต่อรอบ แล้วเขียนผลประเมิน คำแนะนำ และการแจ้งเตือนในแอปในธุรกรรมเดียวต่อผู้เรียน ไม่เคยซิงก์สำเร็จ = ไม่ประเมินอะไร (FR-23) และ `runRiskAssessment` ให้ Admin สั่งเอง
- `functions/lib/thresholds.js`: `listThresholds`/`setThreshold` (OP-04/OP-03) เฉพาะ Admin ตรวจชนิดตัวแปรและช่วงค่า บันทึก audit หมวด `threshold` (เพิ่ม/ตั้งค่า) ไม่เขียนถ้าค่าไม่เปลี่ยน
- `functions/lib/situation.js`: `getLearnerSituation` ใช้ได้ทั้งผู้เรียน (ของตนเอง) และครูที่ปรึกษา (เฉพาะผู้เรียนที่ความสัมพันธ์ active) ผ่าน `requireLearnerAccess` Admin ถูกปฏิเสธเหมือนเดิม คืนสถานะข้อมูล (normal/stale/waiting) ผลประเมินล่าสุดพร้อมเหตุผล คำแนะนำ และการแจ้งเตือน ถ้า waiting ไม่คืนผลประเมินใดเลย
- เพิ่ม index ใน `firestore.indexes.json` (`riskAssessments`, `notifications`) กฎ Firestore เดิมปฏิเสธ collection ใหม่ทั้งหมดอยู่แล้ว (client เข้าถึงผ่าน Backend เท่านั้น)
- ทดสอบ: `npm test` ผ่าน 78 ข้อ (ใหม่ 20 ข้อ: คำนวณแนวโน้ม, เกณฑ์แต่ละตัวแปร, เงื่อนไขแจ้งเตือน, Admin-only, audit, สำเนา threshold ไม่เปลี่ยนตามการแก้ภายหลัง, ไม่แจ้งซ้ำ, ผู้เรียนใหม่, ขอบเขตการเข้าถึง)
- ตัดสินเอง (รอผู้ใช้ยืนยัน): แปลความตัวแปรเป็น เกรด = ค่าเฉลี่ยช่วงล่าสุดต่ำกว่าเกณฑ์, เข้าเรียน/ส่งงาน = เปอร์เซ็นต์ช่วงล่าสุดต่ำกว่าเกณฑ์, แนวโน้ม = จำนวนช่วงที่เกรดเฉลี่ยลดลงต่อเนื่อง >= เกณฑ์ แนวโน้มต้องมีอย่างน้อย 2 ช่วงเวลา ช่วงเวลา (`period`) เทียบเป็นสตริงจึงต้องเรียงตามเวลาได้ ไม่มีกฎเริ่มต้น (ไม่มีกฎ = ไม่มีใครเสี่ยง) ข้อความคำแนะนำเป็นข้อความชั่วคราว
- ยังไม่ได้ทำ: หน้าจอ (แดชบอร์ดผู้เรียน มุมมองครู ตั้งค่า threshold), อีเมล (T-5-04), การแจ้งเตือนถึงครู (ยังไม่กำหนด), ตัวเขียนข้อมูลซิงก์จริง (phase 2 รอข้อมูลระบบเดิม), ไม่ได้ทดสอบกับ emulator ของ Functions/เบราว์เซอร์ ไม่ได้ commit/push

## Phase 4 หน้าจอ (prototype)
- `web/admin/`: เพิ่มส่วนกฎ threshold (ดู/แก้ค่า/เพิ่มกฎ), ปุ่ม "ประเมินความเสี่ยงตอนนี้" (เรียก `runRiskAssessment`) และตัวกรองหมวด `threshold` ในประวัติ
- `web/dashboard/` (ใหม่): ผู้เรียนเห็นภาพรวม 4 ตัวแปร เหตุผลที่เสี่ยง คำแนะนำ ประวัติแจ้งเตือน ป้ายรอข้อมูล/ข้อมูลไม่ทันสมัย ครูที่ปรึกษาเลือกดูผู้เรียนในความดูแล (อ่านอย่างเดียว) บัญชีที่เป็นทั้งสองบทบาทเลือกได้ทั้งตัวเองและผู้เรียนในความดูแล
- `functions/scripts/seed-emulator.js`: เพิ่ม advisor1, ความสัมพันธ์กับ stu-1, ข้อมูลซิงก์ ผลการเรียน และกฎ threshold ตัวอย่าง (stu-1 เสี่ยง, stu-2 ผู้เรียนใหม่)
- ทดสอบมือกับ emulator: admin กดประเมิน ได้ "ประเมินแล้ว 2 คน เสี่ยง 1 คน แจ้งเตือนใหม่ 1 คน", student1 เห็นแดชบอร์ดพร้อมเหตุผล 2 ข้อ (เข้าเรียน 62% < 80%, เกรดลดต่อเนื่อง 2 ช่วง) และคำแนะนำ, advisor1 เห็นผู้เรียนของตน
- ไม่ได้ทดสอบมือ: ป้ายรอข้อมูล/ข้อมูลไม่ทันสมัย (ครอบด้วยเทสต์ฝั่ง Backend เท่านั้น), การแก้ค่า threshold ในหน้า Admin, มุมมองผู้เรียนใหม่ (stu-2), มือถือ ไม่ได้ commit/push

## ทดสอบมือหน้าจอ Phase 4 เพิ่มเติม (emulator)
- ป้ายรอข้อมูล (ไม่มี `lastSuccessAt`): แดชบอร์ดแสดงป้ายเหลือง "รอข้อมูลจากระบบเดิม" และไม่แสดงผลประเมิน คำแนะนำ หรือแจ้งเตือนใดเลย ทั้งที่ในฐานข้อมูลมีผลประเมินเก่าอยู่
- ป้ายข้อมูลไม่ทันสมัย (`status: stale`): ป้ายเหลืองบอกเวลาซิงก์สำเร็จล่าสุด และยังแสดงผลประเมินเดิม
- มือถือ (375x812): แดชบอร์ดและหน้า Admin ไม่มีการเลื่อนแนวนอน พบว่าตาราง threshold ในหน้า Admin บีบจนปุ่ม "บันทึก" หลุดขอบการ์ด จึงทำให้เรียงซ้อนเมื่อจอกว้างไม่เกิน 640px (`#thresholdTable` ใน `web/admin/index.html`)
- แก้ค่า threshold เดิมในหน้า Admin (เข้าเรียน 80 → 50): บันทึกสำเร็จ ประวัติขึ้นค่าก่อน-หลัง
- ยังไม่ได้ทดสอบมือ: มุมมองผู้เรียนใหม่ (stu-2) และมุมมองครูในสถานะรอข้อมูล/ไม่ทันสมัย

## ส่วนรับข้อมูลการเรียนตามรูปแบบกลาง (T-2-02..T-2-08, ยังไม่ผูกกับระบบเดิม)
- `functions/lib/sync.js`: `importLearningData` (Admin) รับ JSON `{ source?, grades[], attendance[], assignments[], assess? }` ตรวจความครบและรูปแบบก่อนเขียนอะไร (ขาดรายการ/ไม่มีข้อมูลเลย = incomplete, แถวผิดรูปแบบ/ซ้ำ = malformed) ถ้าไม่ผ่านจะไม่แตะข้อมูลเดิม บันทึกรอบใน `syncRuns` ตั้ง `syncState` เป็น stale (เคยสำเร็จ) หรือ waiting (ยังไม่เคย) และแจ้ง Admin ที่ active ทุกคน (`notifications` ชนิด `syncFailed`) ถ้าผ่านจะแทนที่ข้อมูลชุดเดิมทั้งหมด (id คงที่ ไม่ซ้ำ) ตั้ง normal และ `lastSuccessAt` แล้วประเมินความเสี่ยงต่อ (ปิดได้ด้วย `assess: false`) แถวของผู้เรียนที่ไม่มี/ไม่ใช่นักศึกษาจะถูกข้ามและรายงาน ไม่ถือว่าล้มเหลว `listSyncRuns` (Admin) ดูรอบล่าสุด
- หน้า Admin: ส่วน "นำเข้าข้อมูลการเรียน" (เลือกไฟล์หรือวาง JSON) และตารางรอบซิงก์ล่าสุด ไฟล์ตัวอย่าง `functions/scripts/sample-learning-data.json`
- เพิ่ม index `users` (status + roles array-contains) ใน `firestore.indexes.json` ที่ขาดไปตั้งแต่ `assessAll` (query เดียวกัน) ใน emulator ไม่ต้องใช้ แต่ Firestore จริงต้องมี
- ทดสอบ: `npm test` ผ่าน 101 ข้อ (ใหม่ 19 ข้อ) ทดสอบมือกับ emulator เริ่มจากยังไม่เคยซิงก์: นำเข้าข้อมูลไม่ครบ → ล้มเหลวและขึ้นในตารางรอบ, นำเข้าตัวอย่าง → สำเร็จ ข้าม ghost 1 คน ประเมิน 2 คน เสี่ยง 1 คน, นำเข้าว่าง → ล้มเหลว (ใช้ข้อมูลเดิม), มือถือไม่ล้นจอ
- ข้อจำกัด/ตัดสินเอง: ไม่ได้ประเมินซ้ำเมื่อรอบล้มเหลวแต่เคยสำเร็จ (design เขียนไว้ว่าประเมินซ้ำด้วยข้อมูลเดิม ได้ผลเท่าเดิมและไม่แจ้งซ้ำจึงข้าม) สาเหตุล้มเหลวแบบระบบเดิมไม่ตอบ/หมดเวลาเกิดไม่ได้จนกว่าจะมีตัวเชื่อม การเขียนเป็นชุดละ 400 รายการ ถ้าล้มกลางทางข้อมูลอาจปนเก่า-ใหม่ (บันทึกเป็นรอบล้มเหลว ชนิด storage) ขนาดสูงสุด 10,000 รายการต่อรอบ ยังไม่ได้ทดสอบกับข้อมูลจำนวนมาก ไม่ได้ commit/push

## ผู้ใช้กำหนดองค์ประกอบเกณฑ์ "ผู้ผ่านเกณฑ์" (FR-27, T-2-10/T-2-11) (2026-10-27)
- องค์ประกอบ: เกรดเฉลี่ยขั้นต่ำ, อัตราเข้าเรียนขั้นต่ำ, อัตราส่งงานขั้นต่ำ ต้องผ่านทุกองค์ประกอบที่ Admin ตั้ง (AND) ไม่รวม "ผ่านรายวิชาที่กำหนด" (ต้องรู้รหัสวิชาและเกณฑ์ผ่านจริงจากระบบเดิม)
- ช่วงเวลา: คำนวณจากช่วงเวลาล่าสุดที่มี (วิธีเดียวกับการประเมินความเสี่ยงใน `risk.js`)
- ไม่มีข้อมูลในองค์ประกอบที่ตั้งไว้ = ไม่ผ่านองค์ประกอบนั้น
- ยังไม่ได้ตั้งเกณฑ์ = ไม่มีใครผ่านเกณฑ์เลย
- แนวทางที่จะทำ (ยังไม่ได้ทำ): `rules` ของ `eligibilityCriteria` (PR #22) ใช้รูปแบบ `{ minGrade?, minAttendanceRate?, minAssignmentRate? }` (องค์ประกอบที่ไม่ใส่ = ไม่ตรวจ) เขียนผลที่ `eligibilityResults/{uid}` หลังนำเข้าข้อมูลสำเร็จและหลัง Admin เปลี่ยนเกณฑ์ ต้องรอ PR #22 เข้า `main` ก่อน
