# การจัดการบัญชีผู้ใช้ บทบาท ความสัมพันธ์ครู-ผู้เรียน และเกณฑ์ผู้ผ่านเกณฑ์

- ID: REQ-20261017-01 | วันที่: 2026-10-17 | สถานะ: Draft
- ดู [[../backlog|Backlog]]
- ส่วนเสริมของ [[20261014-01-student-risk-alert]] (FR-01, FR-07, NFR-01) และ [[20261014-02-peer-advice-chat]] (FR-10, FR-16, NFR-06)

## 1. ที่มา / Requirement ดิบ
พบโดย agent api-db-writer ระหว่างออกแบบ api-spec/db-spec (ดูหัวข้อ "ประเด็นรอตัดสินใจ" ใน `docs/02-design/02-technical/api-spec.md` และ `db-spec.md`): ระบบต้องมีวิธีกำหนดและดูแลบัญชีผู้ใช้ บทบาท (นักศึกษา, ครู/อาจารย์ที่ปรึกษา, อาจารย์, Admin) และความสัมพันธ์ครู/อาจารย์ที่ปรึกษากับผู้เรียนในความดูแล (ที่มาของข้อมูล: นำเข้าจากระบบเดิม LMS/ทะเบียน หรือ Admin จัดการในระบบนี้) รวมทั้งนิยามเกณฑ์ "ผู้ผ่านเกณฑ์" ที่ใช้ตัดสินสิทธิ์ส่งข้อความ (FR-16) และแหล่งข้อมูลของเกณฑ์นั้น ปัจจุบันไม่มี FR/NFR ใดรองรับ

## 2. เป้าหมาย
- ให้ทุกบทบาทและสิทธิ์ที่ spec อื่นอ้างถึงมีที่มาของข้อมูลที่ชัดเจน
- ให้ FR-07 (มุมมองครู/อาจารย์ที่ปรึกษา) รู้ว่าผู้เรียนคนใดอยู่ในความดูแล
- ให้ FR-16 ตัดสินสิทธิ์ผู้ส่งจากเกณฑ์ที่นิยามไว้และตรวจสอบย้อนหลังได้

## 3. ผู้ใช้ / บทบาทที่เกี่ยวข้อง
- Admin (จัดการบัญชี บทบาท ความสัมพันธ์ เกณฑ์), ครู/อาจารย์ที่ปรึกษา (ถูกกำหนดความสัมพันธ์), นักศึกษา (ถูกตัดสินสิทธิ์ผู้ส่ง), อาจารย์ (ผู้ตรวจ)

## 4. Functional Requirements

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|------|-------------|------------|----------------|
| FR-25 | จัดการบัญชีผู้ใช้และบทบาท | ระบบมีบัญชีผู้ใช้และกำหนดบทบาท (นักศึกษา, ครู/อาจารย์ที่ปรึกษา, อาจารย์, Admin) ได้ ข้อมูลตั้งต้นนำเข้าจากระบบเดิม (LMS/ทะเบียน ผ่านกลไกเดียวกับ FR-01) และ Admin เพิ่ม/แก้/ปิดการใช้งานบัญชีและบทบาทในระบบนี้ได้ (ข้อมูลที่ Admin แก้เองไม่ถูกทับโดยการนำเข้าครั้งถัดไป เว้นแต่ Admin สั่ง) นอกจากนี้บัญชีมาจากการ "สมัครเอง" ได้อีกทางหนึ่ง (แก้ 2026-10-27 ดู [[20261027-01-self-registration-and-login]] FR-28) โดยผู้สมัครเองได้เฉพาะบทบาท student สถานะใช้งาน และห้ามเขียนทับบัญชีที่มีอยู่ ที่มาของบัญชีจึงมี 3 ทาง: นำเข้าจากระบบเดิม, Admin จัดการ, สมัครเอง | สูง |
| FR-26 | จัดการความสัมพันธ์ครู/อาจารย์ที่ปรึกษากับผู้เรียนในความดูแล | ระบบเก็บว่าครู/อาจารย์ที่ปรึกษาคนใดดูแลผู้เรียนคนใด นำเข้าจากระบบเดิมได้และ Admin เพิ่ม/ถอน/โอนได้ ผู้เรียนหนึ่งคนมีได้ตั้งแต่ศูนย์ถึงหลายผู้ดูแล มุมมองของ FR-07 แสดงเฉพาะผู้เรียนในความดูแลตามความสัมพันธ์นี้ | กลาง |
| FR-27 | นิยามและประเมินเกณฑ์ "ผู้ผ่านเกณฑ์" | Admin กำหนดเกณฑ์ผู้ผ่านเกณฑ์ที่ตั้งค่าได้ (องค์ประกอบของเกณฑ์ เช่น GPA ขั้นต่ำ หรือผ่านรายวิชา ยังไม่กำหนด) ระบบประเมินเกณฑ์จากข้อมูลที่ซิงก์ตาม FR-01 และให้ผลจริง/เท็จที่ FR-16 ใช้ตัดสินสิทธิ์ส่งข้อความ ผลประเมินเปลี่ยนเมื่อข้อมูลหรือเกณฑ์เปลี่ยน | สูง |

> ระดับความสำคัญของ FR-25..27 ผู้ใช้ยืนยันแล้วเมื่อ 2026-10-17 (ข้อเสนอเดิม: สูงสำหรับ FR-25 และ FR-27 เพราะ FR-16 ที่เป็นสูงและบทบาทผู้ตรวจ FR-13 ต้องพึ่งข้อมูลนี้ใน MVP; กลางสำหรับ FR-26 ตามระดับของ FR-07)

## 5. Non-functional Requirements

| รหัส | ด้าน | ความต้องการ |
|------|------|-------------|
| NFR-07 | ความรับผิดชอบ/audit trail | การเปลี่ยนบัญชี บทบาท ความสัมพันธ์ครู-ผู้เรียน เกณฑ์ผู้ผ่านเกณฑ์ การสมัครเองของผู้ใช้ (เพิ่ม 2026-10-27 ดู [[20261027-01-self-registration-and-login]]) ค่าตั้งการเชื่อมต่อระบบเดิม นโยบายระบบ (เช่น ความถี่ซิงก์ ระยะเวลาล็อก นโยบายแสดงชื่อผู้ส่ง เกณฑ์สัดส่วนรายการนำเข้าที่หาย) และค่า threshold ความเสี่ยง (FR-08 ใน [[20261014-01-student-risk-alert]]) ต้องบันทึกผู้ทำ เวลา และค่าก่อน-หลัง ตรวจสอบย้อนหลังได้ (ต่อยอด NFR-01 และ NFR-05) ระดับ กลาง ผู้ใช้ยืนยันแล้วเมื่อ 2026-10-17 |

## 6. Business Rules
- สิทธิ์ที่ขึ้นกับบทบาทตัดสินจากข้อมูลบทบาทในระบบนี้เท่านั้น
- เฉพาะนักศึกษาที่ผลประเมินเกณฑ์เป็นจริงเท่านั้นส่งข้อความได้ (FR-16)
- ครู/อาจารย์ที่ปรึกษาเห็นเฉพาะผู้เรียนในความดูแล (NFR-01)

## 7. ขอบเขต
- In scope: บัญชีผู้ใช้, บทบาท, ความสัมพันธ์ครู-ผู้เรียน, เกณฑ์ผู้ผ่านเกณฑ์ พร้อมที่มาของข้อมูล (นำเข้า + Admin จัดการ)
- In scope (แก้ 2026-10-27): การยืนยันตัวตน/เข้าสู่ระบบ และการสมัครเองของผู้ใช้ ตาม [[20261027-01-self-registration-and-login]] (FR-28..31) โดยผู้สมัครเองได้เฉพาะบทบาท student เท่านั้น บทบาทอื่นกำหนดโดย Admin หรือนำเข้า
- Out of scope (assumption): บทบาทนอกเหนือ 4 บทบาท

## 8. Acceptance Criteria
- AC-1 (FR-25): ข้อมูลผู้ใช้/บทบาทที่นำเข้าจากระบบเดิมปรากฏในระบบ และ Admin เพิ่ม/แก้/ปิดบัญชีและบทบาทได้
- AC-2 (FR-25): ข้อมูลที่ Admin แก้เองไม่ถูกทับโดยการนำเข้ารอบถัดไป
- AC-3 (FR-26): Admin เพิ่ม/ถอน/โอนความสัมพันธ์ได้ และมุมมองครู/อาจารย์ที่ปรึกษาแสดงเฉพาะผู้เรียนในความดูแล
- AC-4 (FR-27): Admin ตั้งเกณฑ์ได้ และนักศึกษาที่ตรงเกณฑ์ส่งข้อความได้ ส่วนที่ไม่ตรงถูกปฏิเสธตาม FR-16
- AC-5 (FR-27): เมื่อข้อมูลซิงก์หรือเกณฑ์เปลี่ยน ผลผ่านเกณฑ์ของนักศึกษาอัปเดตตาม
- AC-6 (NFR-07): ทุกการเปลี่ยนแปลงข้างต้นมีบันทึกผู้ทำ เวลา ค่าก่อน-หลัง
- AC-7 (NFR-07): การเปลี่ยนค่าตั้งการเชื่อมต่อระบบเดิม นโยบายระบบ และ threshold ความเสี่ยง (FR-08) มีบันทึกผู้ทำ เวลา ค่าก่อน-หลังเช่นกัน

## 9. Assumptions และคำตอบที่ได้จากผู้ใช้
คำตอบจากผู้ใช้ (2026-10-17) ผู้ใช้ยืนยันแล้ว:
- ที่มาของข้อมูลผู้ใช้/บทบาท/ความสัมพันธ์ครู-ผู้เรียน = นำเข้าจากระบบเดิม + Admin แก้ไขในระบบนี้ได้
- เกณฑ์ผู้ผ่านเกณฑ์ = Admin ตั้งเกณฑ์ ระบบประเมินจากข้อมูลที่ซิงก์ตาม FR-01
- ขอบเขต NFR-07 ขยายตามผู้ใช้ 2026-10-17: ครอบคลุมค่าตั้งการเชื่อมต่อ นโยบายระบบ และ threshold ความเสี่ยง (ระดับคงกลาง)
- ระดับความสำคัญ: FR-25 สูง, FR-26 กลาง, FR-27 สูง, NFR-07 กลาง (ตามที่เสนอ)
- ผู้เรียนหลุดเกณฑ์หลังส่งข้อความไปแล้ว = ข้อความที่รอตรวจยังตรวจต่อได้ (พิจารณาสิทธิ์ ณ เวลาส่ง)

- แก้ไข 2026-10-27 (ผู้ใช้ตัดสินใจ): ไม่ตัดการยืนยันตัวตนและการสมัครเองออกจากขอบเขตอีกต่อไป แต่จำกัดว่าสมัครเองได้เฉพาะบทบาท student; FR-25 รวมที่มาแบบสมัครเอง; NFR-07 ครอบคลุมการสมัครเอง

## 10. คำถามที่ยังเปิดอยู่
- องค์ประกอบของเกณฑ์ "ผ่านเกณฑ์" (GPA ขั้นต่ำ, ผ่านรายวิชา, อื่นๆ) และค่าเริ่มต้น (คำถามเปิดเดิมใน [[20261014-02-peer-advice-chat]])
- ความสัมพันธ์ครู-ผู้เรียนใช้ระดับห้อง/กลุ่ม หรือรายบุคคล
- ต้องรัน `/sync-technical-spec` เพื่อให้ api-spec/db-spec มี operation จัดการแทนข้อมูลอ่านอย่างเดียว
