# API Spec (Operation Contract)

สัญญาการทำงานเชิง logical ของ Backend Service ที่ Client และ Scheduler เรียกใช้ ที่มา: [[architecture|High Level Architecture]], [[../feature-list|Feature List]], [[../user-journey|User Journey]], [[../../01-requirements/backlog|Backlog]] ข้อมูลที่ใช้ทุก field ตรงกับ attribute ใน [[db-spec|DB Spec]]

เอกสารนี้เขียนเป็น Operation Contract (ชื่อ operation, ผู้เรียกได้, input, output, กฎทางธุรกิจ, กรณี error) ไม่ระบุรูปแบบการเรียกหรือ protocol ใดๆ เพราะ `technology-stack.md` ยังไม่มีเนื้อหา (ยังไม่ตัดสินใจ) ประเด็นที่ต้องรอ technology อยู่ในหัวข้อ "ประเด็นรอตัดสินใจ"

Spec ต้นทาง: [[../../01-requirements/01-spec/20261014-01-student-risk-alert|REQ-01]], [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|REQ-02]], [[../../01-requirements/01-spec/20261016-01-sync-failure-handling|REQ-03]], [[../../01-requirements/01-spec/20261016-02-peer-chat-recipients-lock-resubmit|REQ-04]], [[../../01-requirements/01-spec/20261016-03-first-sync-failure-and-expired-lock-decision|REQ-05]], [[../../01-requirements/01-spec/20261017-01-user-role-advisor-eligibility-management|REQ-06]]

## 1. กติกากลางของทุก Operation

- ผู้เรียกที่เป็นมนุษย์ต้องผ่านการตรวจตัวตนและสิทธิ์ตามบทบาทที่ Access Control ก่อนทุก operation (NFR-01, NFR-04) Client ไม่ตัดสินสิทธิ์เอง
- ผู้เรียกที่เป็น "ระบบ" คือ Scheduler/โมดูลภายใน Backend Service (ไม่ใช่ผู้ใช้)
- ผลลัพธ์ที่มีข้อมูลผู้เรียนถูกกรองตามสิทธิ์ที่ Backend เสมอ (ผู้เรียนเห็นเฉพาะตน ครูเห็นเฉพาะผู้เรียนใน AdvisorAssignment)
- ชื่อบทบาทตาม [[db-spec#3.2 UserRole (บทบาทของผู้ใช้)|UserRole]]: นักศึกษา (= ผู้เรียน/ผู้ส่ง/ผู้รับ), ครู-อาจารย์ที่ปรึกษา, อาจารย์, Admin (อาจารย์และ Admin = "ผู้ตรวจ" สิทธิ์เท่ากัน)
- สิทธิ์ตามบทบาทตัดสินจากข้อมูลบทบาทในระบบนี้เท่านั้น (UserRole สถานะ "ใช้งาน" ของ User ที่ สถานะบัญชี = ใช้งาน) บัญชีปิดใช้งานทำ operation ใดไม่ได้ (ERR-ACCOUNT-DISABLED) การยืนยันตัวตนหรือเข้าสู่ระบบอยู่นอกขอบเขตตาม REQ-06 สัญญานี้ถือว่าได้ตัวตนผู้เรียกจาก Access Control แล้ว
- operation ที่เปลี่ยนบัญชี บทบาท ความสัมพันธ์ครู-ผู้เรียน เกณฑ์ผู้ผ่านเกณฑ์ ค่าตั้งการเชื่อมต่อ (OP-01) นโยบายระบบ (OP-02) หรือ threshold ความเสี่ยง (OP-03) ต้องบันทึก ConfigChangeAudit (ผู้ทำ เวลา ค่าก่อน-หลัง) ในหน่วยการทำงานเดียวกับการเปลี่ยน (NFR-07) ค่าที่เป็นความลับ (ข้อมูลยืนยันตัวตนกับระบบเดิม) ไม่ถูกคัดลอกลงค่าก่อน-หลัง บันทึกเพียงว่า "เปลี่ยน"
- operation ที่ส่งกลับรายการ (OP-10, OP-13, OP-17..OP-19, OP-23, OP-26, OP-28, OP-32, OP-40, OP-41 และอื่นๆ ที่เป็นรายการ) รองรับการแบ่งหน้า: input "ขนาดหน้า" (ตัวเลข ค่าเริ่มต้นและค่าสูงสุดกำหนดตอน detailed design) และ "จุดต่อ" (ตำแหน่งสุดท้ายของรายการที่ได้รับครั้งก่อน ไม่ใช้หมายเลขหน้า เพื่อไม่ให้รายการซ้ำหรือตกเมื่อมีข้อมูลใหม่เข้ามา) output "จุดต่อถัดไป" (ว่างเมื่อหมดรายการ) ลำดับเรียงของแต่ละ operation ระบุที่ operation นั้น (ค่าเริ่มต้น ล่าสุดก่อน)
- ชื่อ field ตรงกับชื่อ attribute ใน [[db-spec]] ส่วน field ที่ขึ้นต้นด้วย "คำนวณ:" เป็นผลลัพธ์ที่ได้จากข้อมูลหลาย entity ไม่ใช่ attribute ตรงๆ

### Error กลางที่ทุก operation อาจตอบ
| รหัส | ความหมาย | เมื่อเกิด |
|------|----------|-----------|
| ERR-AUTH | ยังไม่ได้ยืนยันตัวตน | ผู้เรียกไม่มีตัวตนที่ตรวจสอบได้ |
| ERR-ACCOUNT-DISABLED | บัญชีถูกปิดใช้งาน | ผู้เรียกมี สถานะบัญชี = ปิดใช้งาน |
| ERR-FORBIDDEN | ไม่มีสิทธิ์ | บทบาทไม่ตรงกับที่ operation อนุญาต หรือขอข้อมูลของผู้เรียนที่ตนไม่มีสิทธิ์เห็น (NFR-01) |
| ERR-NOT-FOUND | ไม่พบรายการ | รหัสที่อ้างไม่มีอยู่ หรือผู้เรียกไม่มีสิทธิ์รู้ว่ามี (เช่น นักศึกษาขอข้อความที่ไม่อนุมัติ ตอบเหมือนไม่มี เพื่อไม่รั่วไหลตาม NFR-04) |
| ERR-INVALID-INPUT | ข้อมูลนำเข้าไม่ถูกต้อง | field จำเป็นขาด ค่านอกชุดที่กำหนด หรือผิดกฎตรวจสอบของ operation นั้น |

### OP-01 ตั้งค่าการเชื่อมต่อระบบเดิม
- FR/NFR: [[../../01-requirements/01-spec/20261014-01-student-risk-alert|FR-01]]
- ผู้เรียกได้: Admin
- Input: ปลายทางระบบเดิม, ข้อมูลยืนยันตัวตนกับระบบเดิม
- Output: ยืนยันการบันทึก, แก้ไขเมื่อ (ไม่ส่งกลับ ข้อมูลยืนยันตัวตนกับระบบเดิม)
- กฎ: มีค่าตั้งที่ใช้งานอยู่ชุดเดียว บันทึกใหม่ทับชุดเดิม บันทึก แก้ไขโดย/แก้ไขเมื่อ ใช้ในรอบซิงก์ถัดไป บันทึก ConfigChangeAudit (หมวด = ค่าตั้งการเชื่อมต่อ, การกระทำ = ตั้งค่า, ผู้ทำ = Admin ผู้เรียก, ค่าก่อน-หลัง เฉพาะ ปลายทางระบบเดิม ส่วน ข้อมูลยืนยันตัวตนกับระบบเดิม บันทึกเพียงว่าเปลี่ยนหรือไม่ ไม่เก็บค่า) ในหน่วยการทำงานเดียวกับการบันทึกค่า การตั้งครั้งแรกมีค่าก่อนว่าง ถ้าไม่มีค่าใดเปลี่ยนจริงไม่บันทึก audit
- Error: ERR-INVALID-INPUT (ค่าว่าง)

### OP-02 ตั้งค่านโยบายระบบ
- FR/NFR: [[../../01-requirements/01-spec/20261014-01-student-risk-alert|NFR-03]], [[../../01-requirements/01-spec/20261016-02-peer-chat-recipients-lock-resubmit|FR-21]], [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|NFR-06]]
- ผู้เรียกได้: Admin (ผู้กำหนดค่าเหล่านี้ spec ไม่ได้ระบุ ใช้ Admin ชั่วคราว ดูประเด็นรอตัดสินใจ)
- Input: ส่งเฉพาะ field ที่จะแก้ได้ ความถี่รอบซิงก์ (ตัวเลข ช่วงเวลา), ระยะเวลาล็อกหมดอายุ (ตัวเลข ช่วงเวลา), นโยบายแสดงชื่อผู้ส่ง (แสดงชื่อ / ซ่อนชื่อ), เกณฑ์สัดส่วนรายการนำเข้าที่หายสูงสุดที่ยังปิดอัตโนมัติ (ตัวเลขเปอร์เซ็นต์ 0-100) (FR-25, FR-26 ตามการตัดสินใจทาง C)
- Output: ค่านโยบายหลังบันทึก
- กฎ: ความถี่รอบซิงก์และระยะเวลาล็อกต้องเป็นตัวเลขมากกว่า 0 ค่าใหม่มีผลกับรอบซิงก์/ล็อกที่เกิดหลังจากนี้ (ล็อกที่ออกไปแล้วคงเวลาหมดอายุเดิม) นโยบายแสดงชื่อมีผลกับการอ่านห้องรวมครั้งถัดไปทันทีโดยไม่แตะข้อมูลข้อความ ([[architecture#6. บันทึกการตัดสินใจเชิงสถาปัตยกรรม|หัวข้อ 6 ประเด็น 4]])
- audit: บันทึก ConfigChangeAudit (หมวด = นโยบายระบบ, การกระทำ = ตั้งค่า, ค่าก่อน-หลังเฉพาะ field ที่เปลี่ยนจริง ครอบคลุม ความถี่รอบซิงก์ ระยะเวลาล็อกหมดอายุ นโยบายแสดงชื่อผู้ส่ง เกณฑ์สัดส่วนรายการนำเข้าที่หาย) ในหน่วยการทำงานเดียวกับการบันทึกค่า ถ้าไม่มีค่าเปลี่ยนจริงไม่บันทึก
- เพิ่มเติม: เกณฑ์สัดส่วนต้องอยู่ระหว่าง 0-100 (0 = ปิดอัตโนมัติได้เฉพาะเมื่อไม่มีรายการหายเลย จึงเท่ากับไม่ปิด) ค่าใหม่มีผลกับรอบนำเข้าถัดไป ([[architecture#4.8 Admin จัดการบัญชี บทบาท ความสัมพันธ์ครู-ผู้เรียน และเกณฑ์ผู้ผ่านเกณฑ์|4.8]])
- Error: ERR-INVALID-INPUT (ค่าไม่ใช่ตัวเลขบวก เกณฑ์สัดส่วนนอกช่วง 0-100 หรือนโยบายนอกชุดที่กำหนด)

### OP-03 ตั้งค่า threshold ความเสี่ยง
- FR/NFR: [[../../01-requirements/01-spec/20261014-01-student-risk-alert|FR-08, FR-03]]

- Output: กฎหลังบันทึก (รหัสกฎ, ตัวแปรที่ประเมิน, ชื่อกฎ, ค่า threshold, แก้ไขเมื่อ)
- กฎ: ตัวแปรที่ประเมินต้องเป็นหนึ่งใน เกรด-ผลการเรียน / การเข้าเรียน / การส่งงาน / แนวโน้มผลการเรียน ค่าใหม่มีผลกับรอบประเมินถัดไปเท่านั้น ผลประเมินเก่าไม่เปลี่ยน (RiskFinding เก็บสำเนา) (AC-2 ของ REQ-01) จุดตัด "รอบถัดไป": OP-07 อ่านชุด threshold ทั้งชุดเมื่อเริ่มรอบประเมิน รอบที่เริ่มแล้วใช้ชุดนั้นตลอดรอบ การบันทึกที่เสร็จหลังรอบเริ่มมีผลรอบถัดไป บันทึก ConfigChangeAudit (หมวด = threshold ความเสี่ยง, การกระทำ = เพิ่ม ถ้าเป็นกฎใหม่ หรือ ตั้งค่า ถ้าแก้กฎเดิม, รหัสกฎที่เกี่ยวข้อง, ค่าก่อน-หลัง) ในหน่วยการทำงานเดียวกับการบันทึกกฎ ถ้าค่าไม่เปลี่ยนจริงไม่บันทึก
- Error: ERR-NOT-FOUND (รหัสกฎไม่มี), ERR-INVALID-INPUT (ตัวแปรนอกชุด หรือค่าไม่ใช่ตัวเลข)

### OP-06 ดำเนินรอบซิงก์ข้อมูล
- FR/NFR: [[../../01-requirements/01-spec/20261014-01-student-risk-alert|FR-01, NFR-03]], [[../../01-requirements/01-spec/20261016-01-sync-failure-handling|FR-19]], [[../../01-requirements/01-spec/20261016-03-first-sync-failure-and-expired-lock-decision|FR-23]]
- ผู้เรียกได้: ระบบ (Scheduler กระตุ้นตาม ความถี่รอบซิงก์)
- Input: ไม่มี (ใช้ค่าจาก LegacyConnectionConfig)
- Output: ผลซิงก์ (สำเร็จ / ล้มเหลวมีข้อมูลเดิม / ล้มเหลวครั้งแรกไม่มีข้อมูลเดิม), รหัสรอบซิงก์
- กฎ:
  0. ก่อนเริ่ม: (ก) ถ้ายังไม่เคยตั้ง LegacyConnectionConfig ไม่เริ่มรอบ ไม่สร้าง SyncRun ไม่เปลี่ยน SyncState และไม่แจ้งใคร (ความล้มเหลวของการเชื่อมต่อต้องมีปลายทางจึงจะเกิดได้) สถานะข้อมูลจึงคงเป็น รอข้อมูล ตามค่าเริ่มต้น และ OP-05 แสดง ตั้งค่าการเชื่อมต่อแล้ว = เท็จ (ข) ถ้ามี SyncRun ที่ จบเมื่อ ว่าง (กำลังทำงานอยู่) ไม่เริ่มรอบใหม่ ไม่สร้าง SyncRun ซ้อน และไม่ถือเป็นความล้มเหลว (ข้อสมมติฐานชั่วคราว)
  1. ขอข้อมูลเกรด การเข้าเรียน การส่งงานจากระบบเดิม ตรวจความครบถ้วนและรูปแบบ
  2. สำเร็จ: บันทึกข้อมูลลง GradeRecord/AttendanceRecord/AssignmentRecord, ตั้ง ซิงก์สำเร็จล่าสุดเมื่อ, สถานะข้อมูล = ปกติ (ป้ายไม่ทันสมัย/รอข้อมูลหายพร้อมกัน) แล้วเรียกตามลำดับ: OP-27 (นำเข้าบัญชี บทบาท ความสัมพันธ์ครู-ผู้เรียนที่มากับข้อมูลซิงก์) → OP-39 (ประเมินผลผ่านเกณฑ์ใหม่ ใช้ข้อมูลที่เพิ่งนำเข้า ถ้า OP-39 ล้มเหลวผลซิงก์ยังเป็นสำเร็จและดำเนินต่อ ผลผ่านเกณฑ์เดิมคงอยู่) → OP-07 สำหรับผู้เรียนทุกคน
  3. ล้มเหลว (ระบบเดิมไม่ตอบสนอง/หมดเวลา/ข้อมูลไม่ครบ/ผิดรูปแบบ) และเคยสำเร็จมาก่อน: ไม่เรียก OP-27 และ OP-39 (ไม่มีข้อมูลใหม่ ผลผ่านเกณฑ์ที่เก็บไว้คงเดิม) ไม่เขียนทับข้อมูลเดิม, สถานะข้อมูล = ไม่ทันสมัย, ผลซิงก์ = ล้มเหลวมีข้อมูลเดิม, สร้าง Notification ชนิดซิงก์ล้มเหลวถึง Admin ทุกคน แล้วเรียก OP-07 ด้วยข้อมูลสำเร็จล่าสุด (ประเมินหลังทุกรอบซิงก์ [[architecture#6. บันทึกการตัดสินใจเชิงสถาปัตยกรรม|หัวข้อ 6 ประเด็น 3]])
  4. ล้มเหลวและไม่เคยสำเร็จ (ไม่เรียก OP-27, OP-39 ด้วย ไม่มีผลผ่านเกณฑ์ใดเกิดขึ้น): สถานะข้อมูล = รอข้อมูล, ผลซิงก์ = ล้มเหลวครั้งแรกไม่มีข้อมูลเดิม, แจ้ง Admin, **ไม่เรียก OP-07** ไม่สร้างผลประเมินหรือแจ้งเตือนความเสี่ยงใดๆ
  5. ข้อมูลไม่ครบ/ผิดรูปแบบ: ปฏิเสธทั้งชุด ปฏิบัติเป็นล้มเหลว (spec ยังเปิดว่าข้ามเฉพาะเรคอร์ดที่ผิดหรือไม่ ดูประเด็นรอตัดสินใจ)
- Error: ไม่ตอบ error แก่ผู้เรียก ความล้มเหลวคือผลซิงก์ที่บันทึก

### OP-07 ประเมินความเสี่ยงผู้เรียน
- FR/NFR: [[../../01-requirements/01-spec/20261014-01-student-risk-alert|FR-02, FR-03, FR-05, NFR-02]], [[../../01-requirements/01-spec/20261016-03-first-sync-failure-and-expired-lock-decision|FR-23]]
- ผู้เรียกได้: ระบบ (ต่อจาก OP-06 ที่ไม่ใช่กรณีล้มเหลวครั้งแรก)
- Input: รหัสรอบซิงก์ที่กระตุ้น (ประเมินผู้เรียนทุกคน)
- ขอบเขตผู้เรียน: ประเมินเฉพาะผู้ที่ สถานะบัญชี = ใช้งาน และมีบทบาท นักศึกษา (ใช้งาน) เท่านั้น (ตรงกับ OP-39) ผู้เรียนที่บัญชีปิดใช้งานหรือถูกถอนบทบาทนักศึกษาไม่ถูกประเมินและไม่ได้รับแจ้งเตือนความเสี่ยง ผลประเมินเดิมที่เก็บไว้ไม่ถูกลบ
- Output: ผลประเมินต่อผู้เรียน (รหัสผลประเมิน, แนวโน้มผลการเรียน, เข้าเงื่อนไขเสี่ยง, ใช้กฎพื้นฐานเท่านั้น, ใช้ข้อมูลซิงก์ ณ, รายการเงื่อนไขที่เข้า)
- กฎ:
  1. ปฏิเสธการทำงานถ้า ซิงก์สำเร็จล่าสุดเมื่อ ว่าง (ไม่ประเมินจากข้อมูลที่ไม่มีอยู่จริง FR-23)
  2. คำนวณ แนวโน้มผลการเรียน จาก GradeRecord ย้อนหลังของผู้เรียน (FR-02) ข้อมูลไม่พอ = ข้อมูลไม่พอ และ ใช้กฎพื้นฐานเท่านั้น = จริง
  3. ประเมิน 4 ตัวแปรด้วย RiskThresholdRule ปัจจุบัน (อ่านทั้งชุดเมื่อเริ่มรอบและใช้ชุดเดียวตลอดรอบ ดู OP-03) ทุกกฎที่เข้าสร้าง RiskFinding พร้อมสำเนา ค่า threshold ที่ใช้, ค่าที่ตรวจพบของผู้เรียน และ คำอธิบายเหตุผล (NFR-02) เข้าเงื่อนไขเสี่ยง = จริง เมื่อมีอย่างน้อย 1 รายการ
  4. สร้าง Recommendation เฉพาะบุคคลจากข้อมูลย้อนหลังของผู้เรียนคนนั้น (ใช้กฎพื้นฐานถ้าเป็นผู้เรียนใหม่) (FR-05)
  5. ผลประเมินทุกครั้งบันทึกถาวรเป็นประวัติ (FR-09) ถ้าเข้าเงื่อนไขเสี่ยงให้เรียก OP-08 เฉพาะเมื่อเข้าเงื่อนไขการแจ้งตามการตัดสินใจ (หัวข้อ 8): ไม่มีผลประเมินก่อนหน้าของผู้เรียนและเข้าเงื่อนไขเสี่ยง, หรือผลก่อนหน้าไม่เสี่ยงและรอบนี้เสี่ยง, หรือทั้งคู่เสี่ยงแต่ชุดกฎที่เข้า (กฎที่เข้า ของ RiskFinding) ต่างกัน ถ้าชุดกฎที่เข้าเหมือนเดิมไม่แจ้งซ้ำ (ผลประเมินยังบันทึกเสมอ)
- Error: ERR-NO-SYNC-DATA (ยังไม่เคยซิงก์สำเร็จ ไม่ประเมินและไม่สร้างข้อมูลใดๆ)

### OP-08 ส่งการแจ้งเตือนความเสี่ยงแก่ผู้เรียน
- FR/NFR: [[../../01-requirements/01-spec/20261014-01-student-risk-alert|FR-04, NFR-02]]
- ผู้เรียกได้: ระบบ (ต่อจาก OP-07)
- Input: รหัสผลประเมิน (ที่ เข้าเงื่อนไขเสี่ยง = จริง และผ่านเงื่อนไขการแจ้งตาม OP-07)
- Output: รหัสการแจ้งเตือน, ผลการส่งรายช่องทาง (ในระบบ, อีเมล)
- กฎ: สร้าง Notification ชนิดความเสี่ยง ถึงผู้เรียนเจ้าของผลประเมิน เนื้อหาต้องมีเหตุผลจาก RiskFinding ทุกรายการ (NFR-02) ส่งทั้งช่องทางในระบบและอีเมล (ไปที่ อีเมล ของ User) บันทึก NotificationDelivery ต่อช่องทาง การส่งอีเมลล้มเหลวไม่ทำให้การแจ้งเตือนในระบบหาย ครูที่ปรึกษาไม่ได้รับแจ้งเตือน (spec ยังเปิดอยู่ ดูได้จาก OP-12 เท่านั้น)
- Error: ERR-INVALID-INPUT (ผลประเมินไม่เข้าเงื่อนไขเสี่ยง)

- Output: สถานะข้อมูล (ปกติ/ไม่ทันสมัย/รอข้อมูล), ซิงก์สำเร็จล่าสุดเมื่อ, ผลประเมินล่าสุด (แนวโน้มผลการเรียน, เข้าเงื่อนไขเสี่ยง, รายการเงื่อนไขที่เข้าพร้อม คำอธิบายเหตุผล), สรุป 4 ตัวแปรจากข้อมูลล่าสุด, คำแนะนำล่าสุด (เนื้อหาคำแนะนำ)
- กฎ: สถานะข้อมูล = รอข้อมูล ⇒ ไม่ส่งผลประเมิน/ตัวแปร/คำแนะนำใดๆ กลับ แสดงเฉพาะสถานะ (FR-23) สถานะข้อมูล = ปกติ (หรือไม่ทันสมัย) แต่ผู้เรียนคนนั้นยังไม่มี RiskAssessment (เช่น เพิ่งเพิ่มบัญชี รอรอบประเมินถัดไป): ส่ง ยังไม่มีผลประเมิน = จริง (คำนวณ) ผลประเมินล่าสุดว่าง คำแนะนำล่าสุดว่าง และสรุป 4 ตัวแปรจากข้อมูลซิงก์ล่าสุดเท่าที่มี (ถ้าไม่มีข้อมูลของผู้เรียนนั้นเลยก็ว่าง) ไม่ส่ง error (OP-12 ใช้กฎเดียวกัน) สถานะ = ไม่ทันสมัย ⇒ ส่งข้อมูลล่าสุดพร้อมสถานะ เพื่อให้ Client แสดงป้าย (FR-19) ป้ายหายเมื่อซิงก์สำเร็จ
- Error: ERR-FORBIDDEN (ผู้เรียกไม่ใช่นักศึกษา)

- กฎ: ส่งเฉพาะการแจ้งเตือนชนิดความเสี่ยงและคำแนะนำ ไม่รวมการแจ้งเตือนของระบบอื่น
- Error: ERR-FORBIDDEN (นักศึกษาขอของผู้อื่น หรือครูขอผู้เรียนนอกความดูแล), ERR-NOT-FOUND (ไม่มีผู้เรียนนี้)

### OP-16 ส่งข้อความใหม่หลังถูกปฏิเสธ
- FR/NFR: [[../../01-requirements/01-spec/20261016-02-peer-chat-recipients-lock-resubmit|FR-22]], [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|FR-10, FR-16, NFR-05]]
- ผู้เรียกได้: นักศึกษาผู้ส่งเดิมที่ EligibilityResult ปัจจุบัน ผ่านเกณฑ์ = จริง (ตรวจใหม่ ณ เวลาส่งใหม่ และบันทึก เกณฑ์ ณ เวลาส่ง ลงข้อความใหม่)
- Input: ข้อความเดิมที่ถูกปฏิเสธ (รหัสข้อความ), เนื้อหาใหม่
- Output: รหัสข้อความใหม่, สถานะ = รออนุมัติ
- กฎ: ข้อความเดิมต้องมีสถานะ ถูกปฏิเสธ และผู้ส่งเดียวกับผู้เรียก ข้อความเดิมไม่ถูกแก้หรือเปิดใหม่ (ปิดถาวร) **ส่งใหม่ได้ครั้งละหนึ่ง** (ผู้ใช้ตัดสินแล้ว): ถ้ามีข้อความใหม่ที่ ข้อความเดิมที่ถูกปฏิเสธ ชี้มายังข้อความเดิมนี้ และสถานะเป็น รออนุมัติ หรือ อนุมัติแล้ว ให้ปฏิเสธ (ERR-RESUBMIT-IN-PROGRESS) ถ้าข้อความใหม่ก่อนหน้าถูกปฏิเสธทั้งหมด ส่งใหม่ได้อีก การตรวจเงื่อนไขนี้ การสร้างข้อความ และการบันทึก audit อยู่ในหน่วยการทำงานเดียวกัน เพื่อกันการส่งซ้อนพร้อมกัน สร้าง ChatMessage ใหม่ที่ ข้อความเดิมที่ถูกปฏิเสธ ชี้ไปข้อความเดิม และบันทึก AuditEvent ชนิดเชื่อมข้อความใหม่กับข้อความเดิม ในหน่วยการทำงานเดียวกับการสร้าง ข้อความใหม่ต้องผ่านการตรวจใหม่ทั้งหมด (ไม่รับการอนุมัติต่อจากเดิม)
- Error: ERR-NOT-FOUND (ไม่ใช่ข้อความของตน), ERR-MESSAGE-NOT-REJECTED (ข้อความเดิมยังไม่ถูกปฏิเสธ), ERR-RESUBMIT-IN-PROGRESS (มีข้อความใหม่ที่โยงกับข้อความเดิมยังรออนุมัติหรืออนุมัติแล้ว), ERR-NOT-ELIGIBLE, ERR-INVALID-INPUT

### OP-17 ดูข้อความที่ฉันส่ง

### OP-18 อ่านห้องรวม
- FR/NFR: [[../../01-requirements/01-spec/20261016-02-peer-chat-recipients-lock-resubmit|FR-20]], [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|FR-11, NFR-04, NFR-06]]

- Error: ERR-FORBIDDEN (ไม่ใช่นักศึกษา)

  2. ข้อความมีล็อก "ใช้งานอยู่" ได้ไม่เกิน 1 รายการ ถ้าผู้อื่นถือล็อกที่ยังไม่หมดอายุอยู่ ปฏิเสธการล็อก (FR-18)
  3. ถ้าล็อกเดิมเลยเวลาหมดอายุแต่ยังไม่ถูกปลด ให้ปลดล็อกเดิม (สถานะล็อก = หมดเวลา, สิ้นสุดเมื่อ) บันทึก AuditEvent ชนิดปลดล็อกอัตโนมัติ สำหรับล็อกเดิม (ผู้กระทำว่าง เหมือน OP-25) และออกล็อกใหม่ พร้อม AuditEvent ชนิดล็อกข้อความ ทั้งหมดในหน่วยการทำงานเดียวกัน (NFR-05 ประวัติล็อกต้องครบ)
  4. lock token ใหม่ทุกครั้ง ไม่ซ้ำกับล็อกใดในระบบ บันทึก AuditEvent ชนิดล็อกข้อความ
  5. ผู้ที่ถือล็อกที่ใช้ได้อยู่แล้วเรียกซ้ำ: คืนล็อกและ token เดิม ไม่ต่ออายุ (สมมติฐานชั่วคราว ดูประเด็นรอตัดสินใจ)
- Error: ERR-ALREADY-LOCKED (ผู้อื่นถือล็อกอยู่), ERR-MESSAGE-CLOSED (ข้อความไม่ได้อยู่สถานะรออนุมัติ), ERR-NOT-FOUND

### OP-21 ขอผลเสนอจาก AI
- FR/NFR: [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|FR-17]] (ระดับต่ำ ไม่บังคับ)
- ผู้เรียกได้: อาจารย์, Admin ที่ถือล็อกที่ใช้ได้ของข้อความนั้น
- Input: รหัสข้อความ, lock token
- Output: ผลที่เสนอ (เชิงลบ / ไม่เชิงลบ)
- กฎ: บันทึก AiSuggestion ผลนี้เป็นเพียงข้อเสนอ ไม่เปลี่ยนสถานะข้อความและไม่แทนการตัดสินของผู้ตรวจ ถ้าบริการ AI ไม่พร้อมหรือไม่ได้เปิดใช้ ผู้ตรวจระบุการระบุเองได้เสมอ (OP-22 ไม่ขึ้นกับ operation นี้) การส่งเนื้อหาข้อความออกนอกระบบยังต้องยืนยัน (คำถามเปิดใน REQ-02)
- Error: ERR-LOCK-INVALID (ไม่ถือล็อกที่ใช้ได้), ERR-AI-UNAVAILABLE (บริการ AI ใช้ไม่ได้ ไม่กระทบการตัดสิน)

### OP-22 ส่งคำตัดสินข้อความ
- FR/NFR: [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|FR-12, FR-13, FR-14, FR-15, FR-18, NFR-04, NFR-05]], [[../../01-requirements/01-spec/20261016-03-first-sync-failure-and-expired-lock-decision|FR-24]]
- ผู้เรียกได้: อาจารย์, Admin
- Input: รหัสข้อความ, lock token, การระบุ (เชิงลบ / ไม่เชิงลบ), ผลตัดสิน (อนุมัติ / ปฏิเสธ), เหตุผลการปฏิเสธ (จำเป็นเมื่อปฏิเสธ), ใช้ผลเสนอ AI (จริง/เท็จ ไม่บังคับ)
- Output: กรณีสำเร็จ: รหัสคำตัดสิน, สถานะข้อความใหม่ (อนุมัติแล้ว/ถูกปฏิเสธ) กรณีไม่สำเร็จ: error ตามด้านล่าง
- กฎ (ทั้งหมดอยู่ใน **หน่วยการทำงานเดียว** สำเร็จพร้อมกันหรือไม่สำเร็จเลย):
  1. ตรวจ input ก่อน: ต้องมี การระบุ เสมอ (FR-12) และถ้าผลตัดสิน = ปฏิเสธ ต้องมีเหตุผลไม่ว่าง (FR-15) ข้อความเชิงลบไม่ถูกปฏิเสธอัตโนมัติ ผู้ตรวจเลือกผลตัดสินเองเสมอ (FR-14)
  2. เทียบ lock token ที่แนบกับล็อก "ใช้งานอยู่" ของข้อความ และตรวจว่าผู้เรียกคือผู้ถือล็อกนั้น และยังไม่ถึงเวลาหมดอายุ
  3. ถ้าถือล็อกที่ใช้ได้: สร้าง ReviewDecision, เปลี่ยนสถานะข้อความเป็น อนุมัติแล้ว/ถูกปฏิเสธ, สิ้นสุดล็อก (สถานะ = สิ้นสุดด้วยคำตัดสิน), บันทึก AuditEvent ชนิดบันทึกคำตัดสิน (ผู้ตรวจ ผล การระบุ เหตุผลอ่านได้ผ่านคำตัดสิน NFR-05)
  4. ถ้าปฏิเสธ: สร้าง Notification ชนิดข้อความถูกปฏิเสธ ถึงผู้ส่ง พร้อมเหตุผล (FR-15) การสร้าง Notification (รายการในระบบ) อยู่ในหน่วยการทำงานเดียวกับข้อ 3 ดังนั้นไม่มีการปฏิเสธที่ผู้ส่งไม่ได้รับแจ้ง ผู้ส่งไม่ได้รับแจ้งเมื่ออนุมัติ (ตาม out of scope ของ REQ-02)
  5. ถ้าไม่ถือล็อกที่ใช้ได้ ไม่ว่าสาเหตุใด (token ไม่ตรง ล็อกหมดเวลา ถูกปลดด้วยมือ ผู้อื่นล็อกต่อ ข้อความถูกตัดสินแล้ว หรือไม่เคยล็อก รวมกรณีเรียกตรงโดยไม่ผ่านหน้าจอ): ปฏิเสธคำตัดสิน **ไม่สร้าง ReviewDecision ไม่เปลี่ยนสถานะข้อความ** (ข้อความอยู่ในคิวรออนุมัติ ไม่หลุดเป็นอนุมัติ) สร้าง Notification ชนิดคำตัดสินถูกปฏิเสธ ถึงผู้เรียก และบันทึก AuditEvent ชนิดคำตัดสินถูกปฏิเสธ พร้อม สาเหตุที่ไม่ถือล็อกที่ใช้ได้ และ lock token ที่แนบมา ทุกสาเหตุปฏิบัติเหมือนกัน (FR-24) AuditEvent และ Notification ของกรณีนี้อยู่ใน **หน่วยการทำงานเดียว** (บันทึกพร้อมกันหรือไม่บันทึกเลย) แต่ผลปฏิเสธคำตัดสินมีผลเสมอ (ไม่สร้าง ReviewDecision ไม่เปลี่ยนสถานะข้อความ) แม้การบันทึกส่วนนี้ล้มเหลว
  6. ไม่เก็บคำตัดสินที่ถูกปฏิเสธเป็นร่าง และไม่ให้ยืนยันซ้ำโดยไม่ล็อกใหม่ (out of scope ของ REQ-05) ผู้ตรวจต้องล็อกใหม่ผ่าน OP-20 แล้วตัดสินใหม่
- Error: ERR-LOCK-INVALID (กฎข้อ 5 ตัวเดียวสำหรับทุกสาเหตุ ผลลัพธ์แจ้งสาเหตุเป็นข้อมูลประกอบเท่านั้น), ERR-NEGATIVITY-MISSING (ไม่ระบุ เชิงลบ/ไม่เชิงลบ), ERR-REASON-MISSING (ปฏิเสธโดยไม่มีเหตุผล) สองตัวหลังเกิดก่อนการเทียบล็อกและไม่สร้าง AuditEvent ชนิดคำตัดสินถูกปฏิเสธ

### OP-23 ดูข้อความที่ถูกล็อกอยู่
- FR/NFR: [[../../01-requirements/01-spec/20261016-02-peer-chat-recipients-lock-resubmit|FR-21]]

### OP-24 ปลดล็อกข้อความด้วยมือ
- FR/NFR: [[../../01-requirements/01-spec/20261016-02-peer-chat-recipients-lock-resubmit|FR-21]], [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|NFR-05]]

- กฎ: ปลดล็อก "ใช้งานอยู่" ของข้อความ (สถานะล็อก = ปลดด้วยมือ, ปลดโดย = ผู้เรียก, สิ้นสุดเมื่อ) ไม่ถือเป็นการตัดสิน สถานะข้อความคงเป็น รออนุมัติ และไม่ปรากฏต่อผู้รับ (NFR-04) บันทึก AuditEvent ชนิดปลดล็อกด้วยมือ ในหน่วยการทำงานเดียวกัน ไม่แจ้งผู้ตรวจเดิมทันที (spec ไม่กำหนด) ผู้ตรวจเดิมจะทราบเมื่อกดตัดสินแล้วถูกปฏิเสธตาม OP-22
- Error: ERR-NO-ACTIVE-LOCK (ข้อความไม่มีล็อกใช้งานอยู่), ERR-NOT-FOUND

- FR/NFR: [[../../01-requirements/01-spec/20261014-02-peer-advice-chat|NFR-05]], [[../../01-requirements/01-spec/20261016-02-peer-chat-recipients-lock-resubmit|FR-22]], [[../../01-requirements/01-spec/20261016-03-first-sync-failure-and-expired-lock-decision|FR-24]]

## 7. กลุ่ม E: บัญชี บทบาท ความสัมพันธ์ครู-ผู้เรียน และเกณฑ์ผู้ผ่านเกณฑ์

อ้างอิงฟีเจอร์ 23-26 และ data flow [[architecture#4.8 Admin จัดการบัญชี บทบาท ความสัมพันธ์ครู-ผู้เรียน และเกณฑ์ผู้ผ่านเกณฑ์|4.8]] spec [[../../01-requirements/01-spec/20261017-01-user-role-advisor-eligibility-management|REQ-06]] operation กลุ่มนี้ที่ผู้เรียกเป็น Admin ทั้งหมดผ่าน Access Control ที่อนุญาตเฉพาะบทบาท Admin (NFR-01) ทุก operation ที่เปลี่ยนข้อมูลบันทึก ConfigChangeAudit ในหน่วยการทำงานเดียวกัน (NFR-07) และบันทึก "ผู้ทำ" เป็น Admin ผู้เรียก

### OP-27 นำเข้าบัญชี บทบาท และความสัมพันธ์จากระบบเดิม
- FR/NFR: [[../../01-requirements/01-spec/20261017-01-user-role-advisor-eligibility-management|FR-25, FR-26, NFR-07]], [[../../01-requirements/01-spec/20261014-01-student-risk-alert|FR-01]]
- ผู้เรียกได้: ระบบ (เรียกจาก OP-06 เมื่อซิงก์สำเร็จ ผ่านกลไกซิงก์เดียวกับ FR-01)
- Input: ข้อมูลที่ระบบเดิมส่งมา: รหัสในระบบเดิม, ชื่อ-นามสกุล, อีเมล, บทบาท, ความสัมพันธ์ครู-ผู้เรียน (ครูที่ปรึกษา-ผู้เรียน)
- Output: สรุป จำนวนที่เพิ่ม, แก้, เปิดกลับ, ปิดอัตโนมัติ (ต่อชนิดรายการ), ข้ามการปิดอัตโนมัติ (พร้อมเหตุผล), ข้ามเพราะ Admin แก้เอง, ข้ามเพราะข้อมูลไม่ถูกต้อง
- กฎ:
  1. จับคู่ผู้ใช้ด้วย รหัสในระบบเดิม ถ้าไม่พบสร้าง User (สถานะบัญชี = ใช้งาน, แหล่งที่มา = นำเข้า) พร้อม UserRole/AdvisorAssignment (สถานะรายการ = ใช้งาน, แหล่งที่มา = นำเข้า)
  2. รายการที่ แหล่งที่มา = นำเข้า: อัปเดตเฉพาะส่วนที่ต่างจากเดิม
  3. รายการที่ แหล่งที่มา = Admin แก้ (รวมบัญชีที่ Admin ปิด บทบาท/ความสัมพันธ์ที่ Admin ถอน): **ไม่ทับ** และไม่เปิดกลับ เว้นแต่ Admin สั่งผ่าน OP-36 (AC-2)
  4. ความสัมพันธ์ที่ครูไม่มีบทบาท ครู-อาจารย์ที่ปรึกษา หรือผู้เรียนไม่มีบทบาท นักศึกษา ข้ามรายการนั้น นับในจำนวนข้ามเพราะข้อมูลไม่ถูกต้อง
  5. บันทึก ConfigChangeAudit (ที่มา = นำเข้าจากระบบเดิม, ผู้ทำว่าง, รอบซิงก์ที่เกี่ยวข้อง, ค่าก่อน-หลัง) เฉพาะรายการที่เปลี่ยนจริง ในหน่วยการทำงานเดียวกับการเปลี่ยนรายการนั้น
  6. รายการที่ แหล่งที่มา = นำเข้า และสถานะ ใช้งาน แต่ไม่ปรากฏในรอบนี้ (หายไป) ตามการตัดสินใจทาง C (หัวข้อ 8) คำนวณแยกต่อชนิดรายการ (บัญชี / บทบาท / ความสัมพันธ์):
     - สัดส่วนที่หาย = จำนวนรายการที่หาย / จำนวนรายการ แหล่งที่มา = นำเข้า ที่ใช้งานอยู่ก่อนรอบนี้
     - ถ้าสัดส่วนไม่เกิน เกณฑ์สัดส่วนรายการนำเข้าที่หายสูงสุด (SystemPolicy): ปิดใช้งานบัญชี (สถานะบัญชี = ปิดใช้งาน) หรือถอนบทบาท/ความสัมพันธ์ (สถานะรายการ = ถอนแล้ว) แหล่งที่มายังเป็น นำเข้า บันทึก ConfigChangeAudit ต่อรายการ (การกระทำ = ปิดใช้งาน / ถอน, ที่มา = นำเข้าจากระบบเดิม, ผู้ทำว่าง, รอบซิงก์ที่เกี่ยวข้อง, ค่าก่อน-หลัง) และสร้าง Notification ชนิดนำเข้าปิดรายการอัตโนมัติ ถึง Admin ทุกคน พร้อมสรุปจำนวนและรายการที่ปิด
     - ถ้าสัดส่วนเกินเกณฑ์ หรือยังไม่ตั้งเกณฑ์: **ไม่ปิดรายการใดของชนิดนั้น** สร้าง Notification ชนิดนำเข้าข้ามการปิดอัตโนมัติ ถึง Admin ทุกคน พร้อมจำนวนที่หาย สัดส่วน และเหตุผลที่ข้าม (เกินเกณฑ์ / ยังไม่ตั้งเกณฑ์) Admin ตัดสินเองผ่าน OP-30, OP-31, OP-34
     - ไม่ปิดบัญชีหรือถอนบทบาท Admin ที่เป็น Admin ใช้งานคนสุดท้าย (ข้ามรายการนั้นและระบุในสรุปแจ้ง Admin)
     - รายการที่ปิดอัตโนมัติและกลับมาปรากฏในรอบนำเข้าถัดไป ขณะ แหล่งที่มา ยังเป็น นำเข้า: เปิดกลับเป็น ใช้งาน พร้อม ConfigChangeAudit (การกระทำ = เปิดใช้งาน / เพิ่ม)
     - Admin เปิดกลับเองผ่าน OP-30 (เปิดใช้งาน), OP-31 (เพิ่มบทบาท), OP-33 (เพิ่มความสัมพันธ์) จะตั้ง แหล่งที่มา = Admin แก้ รายการนั้นจึงไม่ถูกปิดอัตโนมัติซ้ำ
     - รายการที่ แหล่งที่มา = Admin แก้ ไม่ถูกปิดอัตโนมัติ
- Error: ไม่ตอบ error แก่ผู้เรียก ความผิดพลาดของข้อมูลนำเข้านับเป็นรายการที่ข้าม

- Error: ERR-INVALID-INPUT (ขาด field จำเป็น/บทบาทนอกชุด), ERR-DUPLICATE (อีเมลหรือรหัสในระบบเดิมซ้ำ)

- Error: ERR-NOT-FOUND, ERR-INVALID-INPUT, ERR-DUPLICATE (อีเมลซ้ำ), ERR-LAST-ADMIN

- Error: ERR-NOT-FOUND, ERR-INVALID-INPUT (บทบาทนอกชุด/เพิ่มซ้ำที่ใช้งานอยู่/ถอนที่ไม่มี), ERR-LAST-ADMIN

### OP-34 ถอนความสัมพันธ์ครู-ผู้เรียน

### OP-35 โอนผู้เรียนในความดูแลไปครูคนอื่น

### OP-37 ตั้งเกณฑ์ผู้ผ่านเกณฑ์

- กฎ: สร้าง EligibilityCriteria เวอร์ชันใหม่ (เวอร์ชันเดิม + 1) พร้อม EligibilityCriteriaItem เป็นเกณฑ์ปัจจุบัน และตั้งเวอร์ชันก่อนหน้าเป็นไม่ใช่ปัจจุบัน (ไม่แก้ไม่ลบเวอร์ชันเก่า) บันทึก ConfigChangeAudit (การกระทำ = ตั้งเกณฑ์, เกณฑ์ที่เกี่ยวข้อง, ค่าก่อน-หลัง = เกณฑ์เวอร์ชันก่อน-หลัง) ในหน่วยการทำงานเดียวกัน จากนั้นเรียก OP-39 ทันที (สาเหตุ = Admin เปลี่ยนเกณฑ์) ระหว่างรอผลประเมินใหม่เสร็จ ผลเดิมยังใช้ตัดสินสิทธิ์ส่ง (สมมติฐานชั่วคราว) ข้อความที่ส่งแล้วไม่ถูกกระทบ ถ้า OP-39 ล้มเหลว เกณฑ์ใหม่และ audit ยังคงมีผล (ไม่ถอย) ผลผ่านเกณฑ์เดิมคงอยู่ทั้งชุด และระบบประเมินใหม่อีกครั้งเมื่อมีการกระตุ้นถัดไป (ซิงก์สำเร็จ หรือ Admin เปลี่ยนเกณฑ์อีกครั้ง)
- Error: ERR-INVALID-INPUT (ไม่มีองค์ประกอบ หรือค่าว่าง)

- กฎ: ต้องมีข้อมูลซิงก์สำเร็จแล้วและมีเกณฑ์ปัจจุบัน มิฉะนั้นไม่สร้างผลใดและนักศึกษาถือว่าไม่ผ่านเกณฑ์ ประเมินนักศึกษาทุกคน (บัญชีใช้งาน บทบาทนักศึกษา ใช้งาน) จากข้อมูลซิงก์ล่าสุดกับเกณฑ์ปัจจุบัน ผ่านเมื่อทุกองค์ประกอบผ่าน (สมมติฐานชั่วคราว) บันทึก EligibilityResult ทับผลเดิม (ผ่านเกณฑ์, เกณฑ์ที่ใช้, ใช้ข้อมูลซิงก์ ณ, ประเมินเมื่อ, สาเหตุการประเมิน) ไม่แตะข้อความที่ส่งแล้ว (ผู้ส่งที่หลุดเกณฑ์ข้อความที่รออนุมัติยังตรวจต่อได้) ซิงก์ล้มเหลวไม่กระตุ้น operation นี้ การประเมินนักศึกษาทั้งหมดเป็นแบบ "ทั้งชุดหรือไม่เลย": ผลใหม่ทุกรายการถูกบันทึกพร้อมกัน ถ้าเกิดข้อผิดพลาดกลางทางจะไม่เหลือผลใหม่บางส่วน ผลเดิมของทุกคนคงอยู่ (ไม่มีสถานะผสมระหว่างเกณฑ์เก่า-ใหม่) และไม่ลองใหม่เองจนกว่าจะมีการกระตุ้นถัดไป
- Error: ERR-NO-SYNC-DATA (ยังไม่เคยซิงก์สำเร็จ ไม่ประเมิน), ERR-EVALUATION-FAILED (ข้อผิดพลาดระหว่างประเมิน ไม่มีผลใหม่ถูกบันทึก)

กฎตามทาง C (รายละเอียดอยู่ที่ OP-27):
- ใช้กับรายการที่ แหล่งที่มา = นำเข้า เท่านั้น รายการที่ Admin แก้เองไม่ถูกแตะ
- เกณฑ์ข้ามคำนวณแยกต่อชนิดรายการ (บัญชี / บทบาท / ความสัมพันธ์) เป็นสัดส่วนรายการที่หายต่อรายการนำเข้าที่ใช้งานอยู่ก่อนรอบนี้
- ยังไม่ตั้งเกณฑ์ = ไม่ปิดอัตโนมัติ (ปลอดภัยไว้ก่อน) และแจ้ง Admin ว่าข้าม
- การเปิดกลับโดย Admin ตั้ง แหล่งที่มา = Admin แก้ จึงไม่ถูกปิดอัตโนมัติซ้ำ
- ตั้งค่าเริ่มต้นของเกณฑ์ยังไม่กำหนดใน spec จึงว่างไว้จนกว่า Admin ตั้ง

กฎตามทาง B ของการแจ้งเตือนความเสี่ยงซ้ำ (ตีความรายละเอียดเป็นข้อสมมติฐานชั่วคราว):
- เปรียบเทียบผลประเมินรอบนี้กับผลประเมินล่าสุดก่อนหน้าของผู้เรียนคนเดียวกัน (รวมรอบที่ใช้ข้อมูลเดิมจากซิงก์ล้มเหลว)
- แจ้งเมื่อ (1) ไม่มีผลก่อนหน้าและรอบนี้เสี่ยง (2) ก่อนหน้าไม่เสี่ยงและรอบนี้เสี่ยง (3) ทั้งคู่เสี่ยงแต่ชุดกฎที่เข้า (RiskFinding.กฎที่เข้า) ต่างกัน (เพิ่ม ลด หรือสลับ)
- เปรียบเทียบที่ตัวกฎที่เข้า ไม่เปรียบเทียบค่าที่ตรวจพบ (ค่าเปลี่ยนเล็กน้อยแต่กฎเดิมไม่แจ้งซ้ำ)
- ไม่แจ้งเมื่อรอบนี้ไม่เสี่ยง (spec ไม่มีการแจ้งว่าพ้นความเสี่ยง)
- ผลประเมินทุกรอบบันทึกเสมอ (FR-09) การแจ้งเตือนเกิดเฉพาะเมื่อเข้าเงื่อนไขข้างต้น

## 11. ประเด็นรอตัดสินใจ

ประเด็นแจ้งเตือนความเสี่ยงซ้ำตัดสินแล้ว (ทาง B) ดู [[#8. บันทึกการตัดสินใจ|หัวข้อ 8]]

ไม่มีประเด็นเชิงโครงสร้าง/พฤติกรรมที่รอผู้ใช้ตัดสินใจ (ประเด็นรายการนำเข้าที่หายไปตัดสินแล้ว ทาง C ดู [[#8. บันทึกการตัดสินใจ|หัวข้อ 8]])

### ข้อสมมติฐานชั่วคราวที่รอยืนยัน (ไม่กระทบโครงสร้าง)
- นโยบายแจ้ง Admin เมื่อซิงก์ล้มเหลวต่อเนื่อง (OP-06): spec ไม่กำหนด จึงแจ้งทุกรอบที่ล้มเหลว ไม่มีกลไกจำกัดการแจ้งซ้ำ ถ้าผู้ใช้ต้องการจำกัด ต้องกำหนดความต้องการเพิ่ม (อาจกระทบโครงสร้าง เช่น ต้องเก็บสถานะการแจ้งล่าสุด) ยังไม่ออกแบบเพิ่ม
- นโยบายลองส่งอีเมลความเสี่ยงซ้ำเมื่อล้มเหลว (OP-08): spec ไม่กำหนด จึงไม่ลองซ้ำ บันทึก NotificationDelivery สถานะ ล้มเหลว ไว้เท่านั้น ถ้าต้องลองซ้ำ จะต้องเพิ่มข้อมูลจำนวนครั้งที่ลอง (กระทบโครงสร้าง) ยังไม่ออกแบบเพิ่ม และยังไม่มีสถานะ "อ่านแล้ว" ของ Notification
- OP-06 ข้อ 0: ถ้ายังไม่ตั้ง LegacyConnectionConfig ข้ามรอบเงียบๆ (ไม่แจ้ง Admin) และรอบซ้อนถูกข้ามโดยไม่นับเป็นความล้มเหลว การตรวจจับรอบที่ค้างเพราะระบบหยุดกลางทางเป็นประเด็นเชิง technology
- สถานะข้อมูลเริ่มต้นก่อนซิงก์ครั้งแรกคือ รอข้อมูล (ตรงกับ journey ผู้เรียนข้อ 3)
- ผู้ตรวจที่ AI ยังประมวลผลอยู่ขณะล็อกหมดอายุ/ถูกปลด (OP-21): ผลเสนอยังบันทึกได้ ไม่กระทบการตัดสิน (ผลกระทบต่ำ)
- เกณฑ์ผู้ผ่านเกณฑ์: องค์ประกอบยังไม่กำหนด (คำถามเปิดใน REQ-06) เก็บเป็นรายการ (ชนิด + ค่า) ผ่านเมื่อทุกองค์ประกอบผ่าน ยังไม่มีเกณฑ์หรือยังไม่เคยซิงก์สำเร็จ = ไม่มีผู้ผ่านเกณฑ์ (OP-37, OP-39)
- ระหว่างรอ OP-39 ประเมินใหม่หลัง OP-37 ผลเดิมยังใช้ตัดสินสิทธิ์ส่ง
- ความสัมพันธ์ครู-ผู้เรียนเป็นรายบุคคล (ระดับห้อง/กลุ่มเป็นคำถามเปิดใน REQ-06)
- Admin ปิดบัญชี/ถอนบทบาท Admin ของ Admin คนสุดท้ายไม่ได้ (กันระบบไม่มีผู้ดูแล) การปิดบัญชีไม่ปลดล็อกข้อความของผู้ตรวจอัตโนมัติ
- บัญชีที่ Admin เพิ่มเองมีผลผ่านเกณฑ์เมื่อถึงรอบประเมินถัดไป
- ผู้กำหนด ความถี่รอบซิงก์ ระยะเวลาล็อกหมดอายุ และนโยบายแสดงชื่อผู้ส่ง (OP-02) ใช้ Admin ชั่วคราว spec ไม่ได้ระบุผู้กำหนด และค่าเริ่มต้นนโยบายแสดงชื่อ = ซ่อนชื่อ
- ล็อกซ้ำโดยผู้ถือล็อกเดิมที่ยังใช้ได้ (OP-20 กฎข้อ 5): คืนล็อกเดิม ไม่ต่ออายุ
- OP-19 ให้ผู้ตรวจเห็นข้อความเดิมของข้อความที่ส่งใหม่ (คำถามเปิดใน REQ-04 ว่าต้องอ้างอิงให้ผู้ตรวจเห็นหรือไม่)
- ข้อมูลไม่ครบ/ผิดรูปแบบ: ปฏิเสธทั้งชุด (OP-06) จนกว่า spec จะตอบคำถามเปิดของ REQ-03
- ผู้ตรวจอื่นที่ล็อกอยู่ไม่ได้รับแจ้งเมื่อผู้ตรวจเดิมกดตัดสินแล้วถูกปฏิเสธ (คำถามเปิดใน REQ-05) แจ้งเฉพาะผู้ตรวจที่กดตัดสิน
- ครูที่ปรึกษาไม่ได้รับแจ้งเตือน (คำถามเปิดใน REQ-01) ดูได้ผ่าน OP-11/OP-12 เท่านั้น
- ผลที่ AI เสนอบันทึกเมื่อผู้ตรวจขอเท่านั้น ไม่เรียกอัตโนมัติ

### ประเด็นเชิง technology (รอ [[technology-stack]])
- รูปแบบการเรียก operation, วิธียืนยันตัวตนและส่งต่อสิทธิ์, รูปแบบการกระตุ้นของ Scheduler, วิธีทำให้หน่วยการทำงานของ OP-22/OP-20/OP-16/OP-35 และการบันทึก audit ของกลุ่ม E สำเร็จพร้อมกัน และการเรียกบริการ AI ภายนอก ตัดสินที่ technology-stack
